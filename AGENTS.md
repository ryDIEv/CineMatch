# AGENTS.md — правила для ИИ-агента программирования

Этот репозиторий — **собрание проектной документации** CineMatch. Кода в нём нет (каталоги `cinematch/*` пусты). Задача агента — построить проект по документации, не принимая решений за авторов.

## Цель работы

Собрать работающее приложение из этого репозитория так, чтобы поведение совпало с описанным: backend FastAPI с модулем ИИ-агентов и модулем данных, frontend на React, запуск `docker compose up`, подбор трёх фильмов в диалоге, оценки, удаление данных.

Формулировка задачи для агента: «Построй проект по всей описанной документации в данном репозитории». Если документа не хватает — это дефект документации: остановись, перечисли, чего не хватает, и не выдумывай значения.

## Порядок чтения (обязательный)

1. `README.md` — что за продукт, состав, этапы.
2. `documents/overall/contracts.md` — структуры, коды ошибок, `/start`, согласие, `progress`, пределы.
3. `documents/overall/config.md` — переменные окружения, тайм-ауты, целевые значения.
4. `documents/overall/build.md` — структура пакетов, порядок старта, команды, карта «файл → документ».
5. Документация модуля, код которого пишешь: `documents/agents/` (010…165), `documents/data/`, `documents/ui/`.
6. Контракт соседнего модуля, с которым идёт обмен: `130` соответствующего модуля.
7. `documents/rationale.md` — только если нужно понять обоснование, а не поведение.

## Источники истины

| Что | Где | Где его нет |
|---|---|---|
| Поля структур, коды и тексты ошибок, пределы | `documents/overall/contracts.md` | в документах модулей |
| Переменные окружения, тайм-ауты | `documents/overall/config.md` | в `.env.example` (он строится по таблице) |
| Структура кода, команды, порядок старта | `documents/overall/build.md` | в README |
| Тексты промптов | `documents/agents/125.prompts.md` | в коде и в других документах |
| Тексты для пользователя (согласие, отказы, подсказки) | `documents/agents/110.ui-ux.md` | — |
| Требования и сценарии | `075`, `080`, `095` модулей | — |
| Архитектурные решения | `145` модулей | — |

Правило: если два документа расходятся — прав `documents/overall/`; расхождение нужно исправить в том же изменении, а не выбирать удобный вариант.

## Запреты

1. Не добавлять поля, коды ошибок, значения перечней (`type`, `stage`, `kind`, `step`), переменные окружения, которых нет в `documents/overall/`.
2. Не менять контракты без ADR в `145` и одобрения всех трёх модулей.
3. Не писать промпты «по смыслу»: тексты берутся из `125` дословно, плейсхолдеры — из таблицы документа.
4. Не показывать пользователю ошибки, которые возвращаются модели (`INVALID_PARAM`, `UNKNOWN_GENRE`, `NOT_FOUND`).
5. Не вызывать модель до согласия; не давать агенту инструмент удаления данных (только код).
6. Не хранить секреты в коде, журнале и трассе.
7. Не придумывать числа (объём каталога, пороги, тайм-ауты): они есть в `075` модулей и `overall/config.md`.

## Соглашения кода

- Python 3.14, `uv`, Pydantic v2, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic AI.
- Пакеты: `cinematch/overall`, `cinematch/agents`, `cinematch/data`, `cinematch/interfaces/{api,web}`.
- Имена в коде — английские, `snake_case`; тексты для пользователя — русские, из документов.
- Модели — только из `cinematch/overall/contracts.py`; модули их импортируют.
- Промпты — файлы в `cinematch/agents/prompts/`, читаются при старте.
- Один ход диалога — одна функция `handle_user_turn`; прогресс — через `on_progress`.
- Журнал — структурный JSON: `event`, `user_id`, `stage`, `step`, `duration_ms`, `tokens`, `code`.

## Определение готовности

1. `uv run pytest -q` проходит.
2. `python scripts/check_docs.py` не находит расхождений (если скрипт ещё не перенесён — проверь ссылки вручную).
3. `docker compose up --build -d` поднимает backend и frontend; `/api/v1/health` отвечает.
4. Эталонные диалоги из `documents/agents/115.live-prototype.md` воспроизводятся.
5. Сценарии `TS-AG`, `TS-DB`, `TS-UI` из `095` соответствующих модулей проходят.

## Порядок работы

1. Сначала контракты и структура (`overall/`), затем модуль данных, затем агент, затем API и интерфейс — так требует `build.md`.
2. Один модуль — один пакет; не смешивать ответственность (согласие, город, удаление — только оркестратор).
3. Каждый файл писать по документу из карты `build.md §6`; в сообщении коммита указывать документ.
4. После изменения контракта — обновить `overall/`, `AGENTS.md`-таблицу источников и ADR, затем всех потребителей.
