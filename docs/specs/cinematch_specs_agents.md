# 1 ВВЕДЕНИЕ

## 1.1 Наименование программы

Полное наименование программы — «Веб-приложение для диалогового подбора фильмов CineMatch» (далее — программа, CineMatch). Условное обозначение темы разработки — CineMatch.

Настоящее техническое задание (далее — ТЗ) распространяется на общую часть программы и на модуль ИИ-агентов. В проектной документации эти части обозначаются `overall` и `agents`; в коде им соответствуют пакеты `cinematch/overall` и `cinematch/agents`.

## 1.2 Краткая характеристика области применения

Программа предназначена для подбора фильма на вечер в диалоге на естественном языке. Пользователь в свободной форме описывает настроение, свободное время, компанию и пожелания. ИИ-агент с учётом погоды и истории оценок предлагает от одного до трёх фильмов из локального каталога (три, если поиск вернул не меньше трёх) и обосновывает выбор каждого. Оценки просмотренных фильмов учитываются в последующих подборках.

Программа устанавливается на компьютер пользователя и работает в веб-браузере. Данные пользователя хранятся локально.

## 1.3 Границы настоящего технического задания

ТЗ разделено на общую часть и требования к модулю ИИ-агентов. В настоящем ТЗ фиксируются только те свойства этих модулей, которые являются контрактом с общей частью и модулем ИИ-агентов.

# 3 НАЗНАЧЕНИЕ РАЗРАБОТКИ

## 3.1 Функциональное назначение

Функциональное назначение программы — формирование рекомендаций фильмов по описанию ситуации пользователя, ведение диалога о выборе и хранение истории оценок.

Функциональное назначение модуля ИИ-агентов — преобразовать сообщение пользователя в один из допустимых ответов: вопрос, подборку из одного–трёх фильмов с объяснениями, подтверждение выбора или оценки, сообщение об отказе, сообщение об ошибке. Модуль обеспечивает соблюдение обязательных шагов диалога (согласие, город, подтверждение удаления), ограничений и проверку ответа языковой модели.

## 3.2 Эксплуатационное назначение

Программа эксплуатируется локально одним пользователем на персональном компьютере. Модуль ИИ-агентов работает в одном процессе backend вместе с API-слоем и модулем данных; отдельного развёртывания модуля нет.

Архитектура должна допускать переход к нескольким пользователям и подключение других интерфейсов (например, Telegram-бота) без изменения контрактов модуля ИИ-агентов и модуля данных. В MVP такие возможности не реализуются.

Таблица 4 – Роли пользователей

# 4 ТРЕБОВАНИЯ К ПРОГРАММЕ

## 4.1 Общая часть: состав, архитектура и границы модулей

### 4.1.1 Состав программы

Программа должна состоять из трёх модулей и общего слоя. Каждый модуль реализуется одним исполнителем и ведёт собственный комплект документации.

Таблица 5 – Состав программы

| Часть | Назначение | Что не входит |
|---|---|---|
| Общая часть | Модели обмена, коды ошибок, конфигурация, структура кода, журнал | Бизнес-логика модулей |
| Модуль ИИ-агентов | Этапы диалога, классификация, цикл агента, инструменты, промпты, проверка ответа, трасса | Хранение данных, отрисовка интерфейса |
| Модуль данных | Каталог, SQLite, поиск, профиль предпочтений, погода, функции-инструменты | Решения о ходе диалога |
| Модуль интерфейса | REST API, SSE, веб-приложение, карточки, экраны | Обязательные шаги диалога и проверка ответа модели |

### 4.1.2 Архитектура

Программа должна быть построена по схеме:

```text
Браузер → nginx (frontend) → FastAPI /api/v1 → оркестратор → агент (Pydantic AI) → RouterAI
                                                     ├→ реестр инструментов → модуль данных → SQLite
                                                     ├→ TMDB (загрузка каталога)
                                                     └→ Open-Meteo (погода)
```

Требования к архитектуре:

1. Backend — один процесс: API-слой, модуль ИИ-агентов и модуль данных импортируются как пакеты Python; REST между модулями не используется.
2. Агент не обращается к базе данных напрямую: только через реестр инструментов модуля агентов, который вызывает функции модуля данных.
3. Единственное место, где создаётся клиент языковой модели, — модуль агентов; он же считает вызовы, токены и применяет тайм-аут.
4. События хода работы формирует оркестратор; API-слой только перекладывает их в SSE.
5. Инструмента удаления данных у агента нет: согласие, город и удаление выполняет код оркестратора.

### 4.1.3 Границы модуля ИИ-агентов

Таблица 6 – Границы модуля ИИ-агентов

| Внутри модуля (реализует и отвечает исполнитель модуля) | Снаружи (контракт, реализует соседний модуль) |
|---|---|
| Этапы сессии и их инварианты | Определение `user_id` и маршруты REST — API-слой |
| Согласие, выбор города, подтверждение удаления | Хранение пользователя, сессии, выборов, оценок — модуль данных |
| Классификатор запросов (4 класса, 2 промпта) | Поиск по каталогу, профиль, погода — модуль данных |
| Цикл агента, 10 инструментов, промпты | Карточки фильмов `MovieCard` — модуль данных |
| Проверка ответа, повторы, лимиты | Показ карточек, экраны, темы — модуль интерфейса |
| Трасса решений, журнал, события | Транспорт SSE и коды HTTP — API-слой |
| Блокировка одного активного хода на пользователя | Проверка занятости перед открытием SSE — API-слой |

4. Изменение структуры без нового ADR и без одобрения всех трёх исполнителей запрещено.

### 4.1.5 Взаимодействие с соседними модулями

1. **С API-слоем.** API-слой вызывает `handle_user_turn(user_id, message, movie_id=None, on_progress=None)` и `set_consent(user_id, accepted)`; получает `AgentResponse`. Других точек входа у модуля агентов нет.
2. **С модулем данных.** Модуль агентов вызывает девять инструментов (`get_user_ratings`, `get_user_profile`, `get_weather`, `find_movies`, `get_movie_with_credits`, `search_movie`, `save_choice`, `save_rating`, `close_choice`) и служебные функции оркестратора (сессии, согласие, город, настройки, удаление, размер каталога, справочник жанров, неоценённый выбор, очистка просроченных сессий). `user_id` и `exclude_ids` подставляет код; модель их не видит.
3. **С RouterAI.** Запросы к модели идут по API, совместимому с OpenAI Chat Completions, с поддержкой вызова инструментов и структурированного вывода. Адрес, ключ и модель задаются конфигурацией.
4. **С модулем интерфейса.** Модуль агентов не знает о SSE и HTTP: он вызывает переданный обработчик `on_progress(step, text)` и возвращает `AgentResponse`. Тексты для пользователя формируются модулем агентов и берутся из нормативных таблиц.

### 4.1.6 Общие требования к программе

1. Программа должна запускаться одной командой `docker compose up --build -d`; backend и frontend поднимаются вместе, проверка живости — `GET /api/v1/health` с ответом `{"status": "ok", "catalog_size": N}`.
2. Программа должна работать локально для одного пользователя; данные не должны покидать компьютер, кроме обращений к RouterAI, TMDB и Open-Meteo.
3. Интерфейс и ответы агента — на русском языке; имена в коде — на английском, `snake_case`.
4. Программа не должна содержать телеметрии и обращений к сервисам, не перечисленным в 4.9.2.
5. Архитектура должна допускать подключение нового интерфейса и переход к нескольким пользователям без изменения контрактов модуля агентов и модуля данных.
6. Порядок старта backend должен соответствовать 4.9.6; отсутствие обязательной переменной конфигурации — остановка с сообщением `CONFIG_MISSING <имя>`, а не падение на первом запросе.
7. Структура пакетов должна соответствовать `documents/overall/build.md`; общие модели и конфигурация живут только в `cinematch/overall/`.
8. Промпты должны храниться отдельными файлами в `cinematch/agents/prompts/` и читаться при старте; строки промптов в коде не пишутся.

| FR-AG-10 | Отметка «посмотрел X» с поиском фильма и оценкой 1–10 | TS-AG-05 |
| FR-AG-11 | Удаление данных по фразе пользователя после подтверждения; выполняет только код | TS-AG-06 |
| FR-AG-12 | Отказ на сообщения не по теме и небезопасные запросы без вызова агента | TS-AG-07 |

### 4.2.2 Этапы диалога

Модуль должен вести сессию в одном из четырёх этапов. Этапы задают инварианты, которые проверяет код; внутри этапа `dialog` ход разговора определяет агент.

Таблица 9 – Этапы диалога

| Этап | Условие входа | Что делает модуль | Выход |
|---|---|---|---|
| `consent` | Пользователя нет или `users.consent_at` пуст | Показывает правила хранения данных; модель не вызывается | Согласие → `onboarding`; отказ → этап сохраняется |
| `onboarding` | Согласие есть, `users.city` пуст | Разбирает название города, сохраняет вариант | Город сохранён → `dialog`; не найден → этап сохраняется |
| `dialog` | Согласие и город есть | Классификация, агент, подбор, реакции, оценки | `delete_data` → `confirm_delete` |
| `confirm_delete` | Классификатор вернул `delete_data` | Ждёт «да» или «нет», отвечает на вопрос о том, что удалится | `yes` → данные удалены, следующий визит с `consent`; `no` → `dialog` |

Правила восстановления сессии:

1. Сессия живёт 24 часа без активности; каждое сохранение продлевает срок.
2. Источник истины по неоценённому выбору — таблица выборов; `SessionState.pending` — кэш. При расхождении побеждает база.
3. Этап `confirm_delete` не восстанавливается: если сессия истекла, следующий визит ведёт себя как обычный, удаление не выполняется.
4. `/start` этап не меняет; сообщение не попадает в историю, `shown_ids` и трассу.
5. `city_options` живёт в сессии до выбора города или истечения сессии.

### 4.2.3 Согласие на обработку данных

Модуль должен принимать согласие двумя способами, ведущими в одну функцию `set_consent(user_id, accepted)`:

Таблица 10 – Способы принятия согласия

| Способ | Вход | Поведение |
|---|---|---|
| Кнопка интерфейса | `POST /api/v1/consent {"accepted": true\|false}` | Вызов `set_consent`; при `true` сохраняется `users.consent_at`, этап → `onboarding`; при `false` ничего не сохраняется |
| Текст в чате | Сообщение на этапе `consent` | Локальная функция `parse_consent(message)` возвращает `yes` или `no`; модель не вызывается |

`parse_consent` должна быть локальной функцией без обращения к модели:

- `yes` — «да», «принимаю», «согласен», «согласна», «конечно», «ок»;
- `no` — «нет», «не сейчас», «отказываюсь», «не принимаю»;
- любой другой ответ — `no`.

До получения согласия модуль не должен сохранять данные пользователя и обращаться к языковой модели. При отказе показываются те же правила и строка: «Без согласия я не смогу сохранять данные и обращаться к модели. Если передумаете — нажмите «Принимаю» или напишите «принимаю».» Этап остаётся `consent`.

Текст согласия нормативен и изменяется только вместе с ADR-033:

```text
CineMatch хранит ваши сообщения, город, историю выборов и оценок — только на этом компьютере, в локальной базе.

Чтобы подобрать фильм, текст сообщения и краткие сведения о ваших вкусах передаются внешнему провайдеру языковой модели (RouterAI); сервер провайдера может находиться за рубежом. Имя, почта и другие данные, по которым вас можно опознать, не передаются.

Фильмы и постеры приходят из TMDB, погода — из Open-Meteo.

Удалить всё можно одной фразой «удали мои данные» или кнопкой в разделе «Мои данные». Без согласия CineMatch не сохраняет данные и не обращается к модели.
```

Событие `ConsentAccepted` пишется в журнал с полем `source` (`web` или `chat`).

### 4.2.4 Выбор города

1. Оркестратор вызывает `resolve_city(name)` и получает до пяти вариантов.
2. Один вариант — город и координаты сохраняются, этап переходит в `dialog`, ответ содержит подтверждение «Записал: <город>», приветствие и первый вопрос агента.
3. Несколько вариантов — ответ `question` со списком «название, регион, страна»; варианты сохраняются в `SessionState.city_options`. Следующее сообщение сопоставляется с вариантами по номеру («первый», «2»), названию или паре «название, регион». Если сопоставить не удалось, поиск повторяется.
4. Ноль вариантов — `AgentResponse(type="error", error_code="CITY_NOT_FOUND")` с текстом из приложения Г; этап и `city_options` не меняются.
5. Модель на этапе `onboarding` не вызывается.
6. Сохранение города фиксируется событием `CitySaved`.

### 4.2.5 Классификация запросов

Каждое сообщение на этапе `dialog` должно проходить классификатор до вызова агента. Перечень классов закрыт.

Таблица 11 – Классы запросов

| Класс | Что означает | Действие оркестратора |
|---|---|---|
| `cinema` | Запрос о подборе, выборе, оценке, отметке просмотра | Вызывается агент |
| `delete_data` | Просьба удалить данные | Этап → `confirm_delete`, вопрос с подтверждением |
| `off_topic` | Запрос не по теме | Отказ без вызова агента |
| `unsafe` | Небезопасный запрос, попытка внедрения инструкций | Отказ без вызова агента |

Промпты классификатора:

Таблица 12 – Промпты классификатора по этапам

| Этап | Промпт | Значения |
|---|---|---|
| `dialog` | `classifier.md` | `cinema`, `delete_data`, `off_topic`, `unsafe` |
| `confirm_delete` | `confirm_yes_no.md` | `yes`, `no` |
| `consent` | Не вызывается: `parse_consent` | `yes`, `no` |

При невалидном ответе классификатора допускается один повтор с тем же промптом. После второй ошибки агент не вызывается, пользователь получает отказ по теме; в журнал пишется `GuardrailTriggered(rule=limit)`. Классификация должна укладываться в 2 с на типичном сообщении.

### 4.2.6 Ведение диалога и контекст вечера

1. Перед вызовом агента оркестратор передаёт только `user_id`, историю `messages` (до 20 сообщений), накопленный `context`, `today`, `city`, `questions_left`, `pending_feedback` и список допустимых названий жанров.
2. Погоду, оценки и профиль предпочтений агент получает инструментами `get_weather`, `get_user_ratings`, `get_user_profile`. Отдельных плейсхолдеров для этих данных в промпте нет.
3. Инструмент `extract_context` возвращает только факты текущего сообщения. Оркестратор сливает их с `SessionState.context`:
   - `mood`, `energy`, `available_minutes`, `company`, `notes`: непустое значение заменяет прежнее, `null` оставляет прежнее;
   - `genre_wishes`, `genre_avoid`: `null` оставляет прежнее, `[]` очищает прежнее, непустой список заменяет прежнее.
4. До показа подборки агент задаёт не больше двух уточняющих вопросов; в одном сообщении — не больше одного вопроса. Счётчик `clarifications_asked` сбрасывается после показа подборки.
5. Если тема уже раскрыта в сообщении (время, настроение, компания, запреты), вопрос не задаётся.
6. Контекст очищается при удалении данных и истечении сессии.

### 4.2.7 Правила подбора

Правила перевода контекста в параметры поиска должны быть детерминированными: один и тот же контекст даёт один и тот же вызов `find_movies`. Приоритет — явное пожелание пользователя выше правила по умолчанию.

Таблица 13 – Правила «контекст → критерии поиска»

| Контекст | Параметр `find_movies` | Правило |
|---|---|---|
| `available_minutes` задано | `max_runtime` | Жёстко: фильм длиннее не показывается |
| `genre_wishes` не пуст | `genres` | Названия из справочника, логика ИЛИ; неизвестный жанр не передаётся |
| `genre_wishes = null` | `genres` не передаётся | Пожеланий в этом сообщении не было; прежние сохраняются |
| `genre_wishes = []` | `genres` не передаётся | Пользователь явно снял пожелания; прежние очищены |
| `genre_avoid` не пуст | `exclude_genres` | Жёстко: фильм с любым запрещённым жанром не возвращается; реестр объединяет параметр с `context.genre_avoid` |
| `genre_avoid = null` | `exclude_genres` не передаётся | Запретов в этом сообщении не было; прежние сохраняются |
| `genre_avoid = []` | `exclude_genres` не передаётся | Пользователь явно снял запрет; прежний очищен |
| Период назван явно («новинки», «из девяностых») | `year_from`, `year_to` | Только если период назван |
| «проверенное», «с высоким рейтингом» | `min_rating` | Значение передаёт агент; иначе параметр не передаётся |
| `mood = tired`, `energy = low` | Без отдельных параметров | Предпочтение комедии и драмы; хоррор и триллер — только по явной просьбе |
| `company = family` | Без отдельных параметров | Предпочтение семейного кино и маркировки не выше 12+; ужасы и триллеры не предлагаются |
| `company = friends` | Без отдельных параметров | Предпочтение комедий и приключений |
| Дождь, холод | Без отдельных параметров | Уклон в спокойное и тёплое кино; погода — подсказка тона, не фильтр |
| Погода недоступна | — | Блок погоды в ответе не упоминается |

Ослабление критериев допускается только при нехватке результатов и не более двух раз по порядку:

1. Убрать годовые рамки и `min_rating` (жанры и длительность сохраняются).
2. Убрать `genre_wishes`; `genre_avoid` остаётся.

`max_runtime` не ослабляется никогда. Если после двух ослаблений фильмов нет, ответ содержит честное «по этим критериям ничего не нашлось» и предложение изменить пожелания; выдумывать фильмы запрещено. Каждое ослабление фиксируется в трассе шагом «Поиск» с новыми параметрами и результатом.

Если `find_movies` вернул меньше трёх фильмов, показывается столько, сколько есть. Если ноль — ответ без карточек. Возрастная маркировка при `company = family` — мягкое предпочтение, а не ошибка проверки: при отсутствии альтернатив допустим фильм с `NULL` или старшей маркировкой, но агент не утверждает, что фильм разрешён детям.

### 4.2.8 Инструменты агента

Агент должен располагать десятью инструментами. Реестр инструментов проверяет имя и аргументы; вызов вне списка отклоняется.

Таблица 14 – Инструменты агента

| Инструмент | Параметры от модели | Подставляет код | Возвращает | Ошибки модели |
|---|---|---|---|---|
| `extract_context` | `message` | — | `EveningContext` | `INVALID_PARAM` |
| `get_user_ratings` | `limit` (1–50, по умолчанию 20) | `user_id` | До `limit` оценок по убыванию даты | `INVALID_PARAM` |
| `get_user_profile` | — | `user_id` | Веса жанров и актёров, `ratings_count` | — |
| `get_weather` | — | `user_id` | `{city, condition, temp_c, is_day}` или `None` | — |
| `find_movies` | `genres`, `exclude_genres`, `year_from`, `year_to`, `min_rating`, `max_runtime`, `limit` | `user_id`, `exclude_ids` | До `limit` карточек | `INVALID_PARAM`, `UNKNOWN_GENRE` |
| `get_movie_with_credits` | `movie_id` | — | Карточка + `actors`, `overview` | `NOT_FOUND` |
| `search_movie` | `title`, `year` | — | До 5 совпадений | `INVALID_PARAM` |
| `save_choice` | `movie_id` | `user_id`; проверка по `last_shown_ids` | `{choice_id}` | `INVALID_PARAM`, `NOT_FOUND` |
| `save_rating` | `movie_id`, `rating`, `mood_match` | `user_id`, `source` | `{saved, closed_choice_id}` | `INVALID_PARAM`, `NOT_FOUND` |
| `close_choice` | — | `choice_id` из `pending`; `status="dismissed"` | `{closed: true}` | `NOT_FOUND` |

Правила:

1. `user_id` и `exclude_ids` модель не передаёт и не видит; их подставляет реестр инструментов.
2. `exclude_ids` формируется из `SessionState.shown_ids` — все показанные в сессии фильмы, до 50. Оценённые фильмы `find_movies` исключает самостоятельно.
3. Все параметры `find_movies` необязательные. Без критериев фильмы возвращаются по убыванию рейтинга; при переданных жанрах — по числу совпавших жанров, затем по рейтингу, числу голосов и `id`.
4. Жанры объединяются логикой ИЛИ; пустой список равнозначен отсутствию параметра; неизвестное название жанра — `UNKNOWN_GENRE`.
5. `save_choice` принимает только фильм из последней подборки; иное — ошибка, которую видит модель.
6. `exclude_genres` объединяется с `SessionState.context.genre_avoid`: модель может добавить запрет, но не снять запрет пользователя.
7. Ошибка инструмента возвращается модели как результат `{"error": {"code": ..., "message": ...}}` и пользователю не показывается.
8. Инструмента удаления данных, изменения согласия и сохранения города у агента нет.

### 4.2.9 Проверка ответа агента

После ответа модели оркестратор должен выполнить проверки в указанном порядке:

Таблица 15 – Проверки ответа

| № | Что проверяется | При нарушении |
|---|---|---|
| 1 | Схема `AgentOutput` (Pydantic) | Один повтор с `retry_invalid_output.md` |
| 2 | Каждый `movie_id` есть в результате `find_movies` текущего хода | Один повтор, затем `LLM_INVALID_OUTPUT` |
| 3 | Длина `text` ≤ 1200 символов, каждого `reason` ≤ 240 символов | Один повтор, затем `LLM_INVALID_OUTPUT` |
| 4 | Ровно три фильма, если поиск вернул не меньше трёх; иначе — сколько вернул поиск | Один повтор, затем `LLM_INVALID_OUTPUT` |
| 5 | В `kind = question` не больше одного вопроса | Один повтор, затем `LLM_INVALID_OUTPUT` |
| 6 | Ни один фильм не содержит жанр из `genre_avoid`; длительность не больше `available_minutes` | Один повтор, затем `LLM_INVALID_OUTPUT` |

Повторов не больше одного на ход. Второй невалидный ответ пользователю не показывается: возвращается `AgentResponse(type="error", error_code="LLM_INVALID_OUTPUT")`. Фильм вне результатов поиска, длиннее свободного времени или с запрещённым жанром не показывается ни при каких условиях.

### 4.2.10 Реакция на подборку, выбор и оценки

1. Реакция пользователя распознаётся агентом; отдельного эндпоинта выбора нет. Нажатие на карточку отправляет обычное сообщение «Выбираю «…»» с подсказкой `movie_id`; решение о реакции принимает агент.
2. Выбор сохраняется инструментом `save_choice`; оркестратор проверяет, что фильм входит в последнюю подборку, и отвечает подтверждением с названием и годом.
3. Просьба о других вариантах — новый вызов `find_movies` с прежними или изменёнными критериями; показанные фильмы исключаются кодом. Если новых нет — честный ответ и предложение изменить критерии.
4. Отказ («в другой раз») завершает подбор коротким сообщением; выбор не сохраняется.
5. Неоценённый выбор: при `/start` на этапе `dialog` оркестратор вызывает `get_pending_feedback` и возвращает `feedback_question` с названием и годом. Агент спрашивает оценку 1–10 и подошёл ли фильм под настроение (`yes`, `partly`, `no`).
6. Оценка сохраняется `save_rating` с `source="after_choice"`; выбор закрывается. «Не смотрел» — `close_choice(status="dismissed")`, оценка не сохраняется. Оценка вне 1–10 — `INVALID_PARAM` модели и один уточняющий вопрос.
7. Отметка просмотренного без CineMatch: агент вызывает `search_movie(title, year)`. Одно совпадение — `save_rating(..., source="manual")`; несколько — вопрос с годами; ноль — просьба уточнить название. Если оценка не названа — один вопрос об оценке.
8. Оценки и профиль предпочтений учитываются в последующих подборках через `get_user_ratings` и `get_user_profile`.

### 4.2.11 Удаление данных

1. Классификатор возвращает `delete_data`; оркестратор переводит сессию в `confirm_delete` и задаёт нормативный вопрос: «Удалить оценки, историю и настройки? Это действие нельзя отменить. Ответьте «да» или «нет».»
2. `yes` — оркестратор вызывает `delete_user_data(user_id)`, очищает сессию и отвечает «Готово, данные удалены.» Следующий визит начинается с `consent`.
3. `no` — этап возвращается в `dialog`, данные сохраняются; ответ: «Хорошо, оставил как было. Чем помочь с выбором?»
4. Вопрос о том, что удалится, определяется локально по наличию `?` или слов «что», «какие», «как»; классификатор не вызывается, этап не меняется, ответ: «Удалятся оценки, история выборов, город и настройки. Каталог фильмов останется. Ответьте «да» или «нет».»
5. Невалидный ответ дважды — этап возвращается в `dialog`, удаление отменяется.
6. Если пользователь ушёл на этапе подтверждения, сессия истекает и удаление не выполняется.
7. Удаление выполняет только код; инструмента удаления у агента нет. Событие `UserDataDeleted` содержит только счётчики удалённых записей.

### 4.2.12 Отказы на запросы не по теме и небезопасные запросы

1. Классы `off_topic` и `unsafe` обрабатываются без вызова агента.
2. Тексты нормативны: для `off_topic` — «Я помогаю только с выбором фильмов. Расскажите, какое настроение и сколько есть времени, — подберу что-нибудь на вечер.»; для `unsafe` — «С этим не помогу. Могу подобрать фильм на вечер — расскажите о настроении.»
3. Отказ не предлагает меню и не перечисляет возможности.
4. В журнал пишется `OffTopicRejected` с классом; текст сообщения пользователя не записывается.
5. После двух ошибок классификатора поведение безопасное: агент не вызывается, пользователь получает отказ по теме.

### 4.2.13 Трасса решений

1. Каждая подборка должна сопровождаться трассой `AgentTrace[]`: шаг, действие, результат.
2. Шаг определяет код по инструменту: `extract_context` → «Контекст»; `get_weather` → «Погода»; `get_user_ratings`, `get_user_profile` → «Оценки»; `find_movies`, `search_movie`, `get_movie_with_credits` → «Поиск»; проверка ответа → «Проверка».
3. `action` и `summary` формирует код из имени инструмента и его результата; модель их не пишет.
4. В трассе не должно быть системных промптов, ключей, `user_id` и служебных путей.
5. Трасса входит в `AgentResponse` и в журнал; при ходе без агента она пуста.

### 4.2.14 Сообщения о ходе работы

`handle_user_turn` должен принимать необязательный обработчик `on_progress(step, text)`. События формирует оркестратор; API-слой перекладывает их в SSE.

Таблица 16 – События хода работы

| `step` | Когда | Фраза |
|---|---|---|
| `classify` | Сразу при приёме сообщения, до классификатора | «Определяю, что вы написали…» |
| `tool` | Перед вызовом инструмента | «Разбираю, что вы описали…», «Смотрю ваши оценки…», «Проверяю погоду…», «Ищу фильмы…», «Уточняю детали…», «Сохраняю…» |
| `check` | После ответа модели, до сборки ответа | «Проверяю подборку…» |

Правила:

1. Первое событие `classify` отправляется до обращения к модели; интерфейс обязан показать реакцию не позже 1 с.
2. `text` — готовая фраза для пользователя, без параметров и названий инструментов. Набор фраз закрыт.
3. События не входят в `AgentResponse`, не дублируются в трассе и не сохраняются в истории.
4. Для одного сообщения допустимо несколько `tool`; порядок и количество определяет агент.
5. Ошибка обработчика не прерывает ход и записывается в журнал.

### 4.2.15 Промпты

Промпты должны храниться отдельными файлами и читаться при старте. Версия промптов — 1.1.

Таблица 17 – Файлы промптов

| Файл | Когда используется | Модель | Температура |
|---|---|---|---|
| `system_agent.md` | Системный промпт агента на каждом ходе | `LLM_MODEL` | 0.3 |
| `classifier.md` | Этап `dialog`: класс запроса из 4 значений | `LLM_CLASSIFIER_MODEL` | 0 |
| `confirm_yes_no.md` | Этап `confirm_delete`: `yes`/`no` | `LLM_CLASSIFIER_MODEL` | 0 |

Правила:

1. В шапке каждого файла — версия, дата и ссылка на нормативный документ промптов.
2. Плейсхолдеры в фигурных скобках подставляет код; модель не видит `user_id`, ключи, пути и содержимое `.env`.
3. Текст пользователя никогда не подставляется в системный промпт: промпт идёт системным сообщением, текст пользователя — отдельным сообщением с ролью `user`.
4. Изменение текста промпта — запрос на слияние с прогоном эталонных пар и записью результата; изменение без прогона не принимается.
5. Суммарный размер системного промпта и контекста — не более 30 000 входных токенов на сообщение.

### 4.2.16 Защита от внедрения инструкций

Модуль должен обеспечивать защиту следующими мерами:

1. Ответы классификатора и `extract_context` ограничены схемой (перечень значений или `EveningContext`), поэтому внедрённая инструкция не может изменить формат ответа.
2. Агент вызывает только инструменты из фиксированного списка; вызов вне списка отклоняется реестром.
3. Инструменты записи проверяют аргументы по состоянию сессии; `user_id` и исключения подставляет код.
4. Описания фильмов и прочие данные TMDB рассматриваются как данные, а не как инструкции.
5. Системный промпт не раскрывается; ключи и служебные идентификаторы в запросах к модели отсутствуют.
6. Устойчивость проверяется на наборе из 20 атак; успешных раскрытий промпта и выполнения внедрённых инструкций должно быть 0.

### 4.2.17 Журналирование и события

## 4.3 Требования к надёжности

Таблица 20 – Поведение при отказах

| Ситуация | Требуемое поведение |
|---|---|
| Ошибка модели или сети | Один повтор запроса; затем `LLM_UNAVAILABLE`; этап диалога сохраняется |
| Невалидный ответ модели | Не более одного повтора; невалидный ответ не показывается; затем `LLM_INVALID_OUTPUT` |
| Тайм-аут запроса к модели (20 с) | Один повтор, затем `LLM_UNAVAILABLE` |
| Ход дольше 45 с | `LIMIT_EXCEEDED` от оркестратора |
| Ожидание в API-слое дольше 60 с | `AGENT_TIMEOUT`; поток завершается событием `error` |
| Погода недоступна | Подбор без погоды; блок погоды не упоминается |
| Каталог пуст | `CATALOG_EMPTY` до классификатора и агента; backend продолжает работать |
| База данных недоступна | `DATA_UNAVAILABLE` |
| Второе сообщение во время первого хода | `SESSION_BUSY`; сессия первого хода не перезаписывается |
| Отсутствует обязательная переменная конфигурации | Backend не стартует, в журнале `CONFIG_MISSING <имя>` |

Дополнительные требования:

1. Данные пользователя и каталог должны сохраняться между перезапусками программы.
2. Сохранность данных между перезапусками и целостность записей обеспечивает модуль данных; конкретные параметры хранения определяются ТЗ модуля данных.
3. Сессия истекает через 24 часа без активности; просроченные сессии удаляются при старте.
4. Блокировка хода снимается в `finally`, в том числе при тайм-ауте; при перезапуске процесса блокировки исчезают вместе с процессом.
5. Ошибка обработчика `on_progress` не прерывает ход.

## 4.4 Требования к информационной безопасности

1. Согласие запрашивается до начала обработки данных и содержит отдельный пункт о передаче текста сообщений внешнему провайдеру языковой модели, в том числе зарубежному.
2. В запросах к модели не передаются служебные идентификаторы (`user_id`, ключи, пути). Текст сообщения передаётся провайдеру, как указано в согласии; история оценок — парами «фильм — оценка».
3. Данные пользователя хранятся только на его компьютере; удаление данных одной фразой после подтверждения удаляет согласие, настройки, сессии, выборы и оценки.
4. Ключи доступа хранятся только в `.env`; они не попадают в журнал, трассу, ответы и репозиторий.
5. Агент вызывает только разрешённые инструменты; инструмента удаления данных у агента нет; согласие, город и удаление выполняет только код.
6. Запросы к базе данных выполняются только с подстановкой параметров; конкатенация значений в строку запроса запрещена.
7. При попытке внедрения инструкций через текст пользователя или описания фильмов программа не раскрывает системный промпт и не выполняет внедрённые инструкции; проверка — на наборе из 20 атак.
8. Журнал не содержит текста сообщений, промптов и персональных данных; события содержат только классы, коды и счётчики.

## 4.5 Требования к временным характеристикам

Таблица 21 – Целевые значения и тайм-ауты

| Параметр | Значение | Тип | Где задаётся |
|---|---|---|---|
| Ответ на одно сообщение | ≤ 10 с для 95 % сообщений | Цель (NFR-AG-01) | — |
| Полный подбор, включая ответы пользователя | ≤ 60 с | Цель (NFR-AG-02) | — |
| Классификация запроса | ≤ 2 с | Цель (NFR-AG-03) | — |

Целевые значения должны быть меньше соответствующих тайм-аутов.

## 4.6 Требования к качеству функционирования

Качество работы модуля должно измеряться на фиксированных наборах; результаты нельзя выдумывать — без ключа RouterAI прогон не выполняется.

Таблица 22 – Метрики качества

| Метрика | Как считается | Порог |
|---|---|---|
| Соответствие схеме | Доля ответов, прошедших `AgentOutput` без повтора | ≥ 95 % |
| Корректность `kind` | Совпадение с ожидаемым в 10 эталонных парах | ≥ 8 из 10 |
| Число `movie_ids` | Совпадение с ожидаемым в 10 эталонных парах | ≥ 8 из 10 |

| Раскрытие промпта | Число успешных атак | 0 |
| Время ответа | p95 на 10 полных подборах | ≤ 10 с |
| Токены | Сумма `tokens_in` и `tokens_out` на подбор | ≤ 30 000 входных |

Протокол: загрузить фикстуру каталога; прогнать 10 эталонных пар как быструю проверку промптов; прогнать 30 диалогов; прогнать 20 атак; повторить для каждого кандидата при одинаковых температуре и промптах; выбрать модель по порогам, затем по p95 и стоимости; результат записать с именем модели и версией промптов. Для выбранной модели прогон повторяется три раза.

### 4.9.6 Порядок старта backend

1. Прочитать `.env` и переменные окружения; проверить обязательные (`TMDB_API_KEY`, `LLM_API_KEY`, `LLM_MODEL`). При отсутствии — остановиться с сообщением `CONFIG_MISSING <имя>`.
2. Загрузить промпты из `cinematch/agents/prompts/`; отсутствие файла — ошибка старта.
3. Открыть SQLite по `CINEMATCH_DB_PATH`, включить WAL и внешние ключи.
4. Применить миграции: `alembic upgrade head`.
5. Выполнить `purge_expired()` — удалить просроченные сессии.
6. Зарегистрировать маршруты, включая `/api/v1/health`.
7. Записать в журнал `backend ready` и начать принимать запросы.

Если каталог пуст, backend стартует: `/health` возвращает `catalog_size: 0`, а запрос подбора получает `CATALOG_EMPTY`.

## 4.12 Специальные требования

1. Каждая карточка фильма содержит возрастную маркировку `0+`, `6+`, `12+`, `16+` или `18+` в соответствии с Федеральным законом № 436-ФЗ; при отсутствии данных — `null`, и агент не утверждает, что фильм разрешён детям.
2. Интерфейс и ответы агента — на русском языке. Управление подбором выполняется текстом; кнопки используются на экране согласия и для перехода между экранами. В ответах агента нет markdown и эмодзи.
3. На одно сообщение — не более 8 обращений к языковой модели и не более 30 000 входных токенов; для ключа RouterAI задаётся лимит расходов.
4. Системные промпты хранятся отдельными файлами и изменяются через запросы на слияние.
5. Все данные привязаны к идентификатору пользователя, который определяется в одном месте API-слоя; это обеспечивает переход к нескольким пользователям без изменения схемы данных.
6. Агент не выдумывает фильмы, годы, длительность и факты: сведения берутся из карточек каталога; при отсутствии данных поле не используется в объяснении.
7. Если ответ модели не соответствует правилам, пользователь видит сообщение об ошибке из каталога, а не «примерный» ответ.

| `CATALOG_EMPTY` | Данные | Пользователь | «Каталог фильмов пуст. Запустите загрузку каталога.» |
| `DATA_UNAVAILABLE` | Данные | Пользователь | «База данных недоступна. Попробуйте позже.» |
| `LLM_UNAVAILABLE` | Агенты | Пользователь | «Сервис подбора временно недоступен. Попробуйте через минуту.» |
| `LLM_INVALID_OUTPUT` | Агенты | Пользователь | «Не получилось подобрать фильмы. Попробуйте переформулировать запрос.» |
| `LIMIT_EXCEEDED` | Агенты | Пользователь | «Подбор занял слишком много времени. Попробуйте уточнить запрос.» |
| `INPUT_TOO_LONG` | Агенты | Пользователь | «Сообщение длиннее 1000 символов. Сократите его.» |
| `INVALID_INPUT` | API | Пользователь | «Пустое сообщение.» |
| `AGENT_TIMEOUT` | API | Пользователь | «Агент не ответил. Попробуйте ещё раз.» |
| `SESSION_BUSY` | API | Пользователь | «Дождитесь ответа на предыдущее сообщение.» |

Правила: ошибки, которые возвращаются модели, пользователю не показываются; остальные показываются дословно; каждая ошибка пишется в журнал полями `event=error`, `code`, `layer`, `user_id`, `stage`, `duration_ms`, `retry`; текст сообщения в журнал не попадает.

# ПРИЛОЖЕНИЕ Е. Передача требований в ТЗ модулей данных и интерфейса

Настоящее приложение фиксирует границу: что уже определено этим ТЗ и должно быть принято следующими ТЗ как входные данные. Внутренних требований к модулям данных и интерфейса настоящее ТЗ не устанавливает.

## Е.1 Для ТЗ модуля данных

Перечисленное ниже — контракт со стороны модуля агентов; ТЗ модуля данных принимает его как входные данные и раскрывает внутренние решения самостоятельно.

1. Девять функций-инструментов с сигнатурами и семантикой из 4.2.8: `get_user_ratings`, `get_user_profile`, `get_weather`, `find_movies`, `get_movie_with_credits`, `search_movie`, `save_choice`, `save_rating`, `close_choice`.
2. Служебные функции, недоступные модели: сохранение согласия, поиск и сохранение города, настройки пользователя, чтение и запись сессии, создание сессии, неоценённый выбор, удаление данных пользователя, размер каталога, справочник жанров, очистка просроченных сессий.
3. Состав хранимых данных, который требуется контрактом: пользователи и согласие, настройки, сессии (24 часа), выборы (не более одного `pending` на пользователя), оценки 1–10. Источник истины по неоценённому выбору — таблица выборов.
4. Семантика `find_movies`: оценённые фильмы исключаются всегда; показанные — по `exclude_ids`; жанры объединяются по ИЛИ; порядок — по числу совпадений, затем по рейтингу, голосам и `id`; неизвестный жанр — `UNKNOWN_GENRE`.
5. Коды `INVALID_PARAM`, `UNKNOWN_GENRE`, `NOT_FOUND`, `CITY_NOT_FOUND`, `CATALOG_EMPTY`, `DATA_UNAVAILABLE` в случаях, заданных контрактом.
6. Требование контракта: данные сохраняются между перезапусками, записи целостны; конкретные параметры хранения определяет ТЗ модуля данных.
7. Загрузка каталога, кэширование погоды и расчёт профиля предпочтений определяются ТЗ модуля данных; для модуля агентов обязателен только контракт функций из 4.2.8.
8. Состав полей и кодов не расширяется без ADR и согласования; семантика функций не меняется без нового ADR.

## Е.2 Для ТЗ модуля интерфейса

1. REST API с базовым путём `/api/v1` входит в контракт: `GET /health`, `GET /session`, `POST /consent`, `POST /messages` (SSE), `GET /history`, `GET /cities`, `PUT /settings`, `DELETE /me`.
2. При открытии страницы: `GET /session`, затем `POST /messages` с текстом `/start`; `/start` не попадает в историю.
3. Нажатие на карточку отправляет сообщение «Выбираю «…»» с `movie_id`; отдельных эндпоинтов выбора и оценки нет.
4. Передавать события `progress`, `response`, `error`; шаги `classify`, `tool`, `check` и фразы не придумывать, а брать из контракта. При `catalog_size == 0` — `503 CATALOG_EMPTY` до открытия SSE; при занятом пользователе — `409 SESSION_BUSY` до открытия SSE; пустой или длинный текст — `400`.
5. Отображать карточки с постером, названием, годом, длительностью, рейтингом, возрастной маркировкой и объяснением; раскрываемый блок «Как агент выбирал» с трассой.
6. Не реализовывать в интерфейсе согласие, выбор города и удаление как бизнес-логику: только вызовы контракта и отображение ответов.
7. Использовать тексты для пользователя из нормативных таблиц модуля агентов; собственных формулировок ошибок и отказов не вводить.

## Е.3 Что остаётся открытым и решается в следующих ТЗ

1. Схема таблиц, индексы, миграции, объём и параметры загрузки каталога, порог голосов — ТЗ модуля данных.
2. Формулы профиля предпочтений, кэширование геокодирования, обработка кодов WMO — ТЗ модуля данных.
3. Состав экранов, компоненты, темы, адаптивность, доступность, обработка состояний загрузки и ошибок на клиенте — ТЗ модуля интерфейса.
4. Аутентификация, несколько пользователей, Telegram-бот, CLI, локальная модель — будущий функционал, в MVP не входят.
