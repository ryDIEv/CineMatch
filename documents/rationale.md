## 1. Задача и требования

Выбор фильма на вечер зависит от факторов, которые каталоги и фильтры не учитывают: настроения, усталости, свободного времени, компании, погоды. Пользователь долго перебирает подборки, а найденный фильм часто не подходит к ситуации.

CineMatch решает задачу в форме короткого диалога. Пользователь описывает ситуацию своими словами, система предлагает три фильма из реального каталога и объясняет выбор.

Требования, по которым оцениваются решения в этом документе:

| Код | Требование |
|---|---|
| К1 | Свободный текст на русском языке на входе |
| К2 | Учёт контекста: настроение, время, компания, погода, история оценок |
| К3 | Только существующие фильмы с достоверными сведениями |
| К4 | Объяснение каждой рекомендации и открытый ход решения |
| К5 | Работа с первого запуска, без накопленной истории оценок |
| К6 | Локальный запуск; один пользователь в MVP, архитектура с расчётом на нескольких |
| К7 | Ограничения учебного проекта: команда из трёх человек, срок до 20.12.2026, минимальный бюджет, доступность сервисов и оплаты из России |

Ближе всего к CineMatch по данным Кинопоиск. В конце 2025 года он перевёл рекомендации на нейросетевую модель и добавил объяснение под постером [1]. Объяснение остаётся подписью к ленте, ход решения пользователю не показывается, а диалоговый ассистент на начало октября 2026 года только анонсирован [2]. Универсальные ассистенты ведут диалог, но не гарантируют существование названных фильмов и не знают истории оценок пользователя.

Сочетание диалога, контекста вечера, реального каталога и открытого хода решения в рассмотренных сервисах не встречается. CineMatch не конкурирует с ними по объёму каталога и аудитории. Предмет проекта — архитектура агентной рекомендательной системы с проверяемыми рекомендациями.

## 3. Подходы к построению рекомендаций

### 3.1. Основные подходы

Рекомендательная система оценивает полезность объекта для пользователя и предлагает объекты с наибольшей оценкой [4, 5].

- **Коллаборативная фильтрация** (collaborative filtering) использует матрицу оценок «пользователь × объект». Фильм рекомендуется, если его высоко оценили пользователи со схожими вкусами (user-based) или если он похож по оценкам на уже понравившиеся (item-based). Матричная факторизация представляет пользователей и объекты векторами скрытых факторов [6]. Подходу нужно много пользователей и оценок.
- **Контентная фильтрация** (content-based) сравнивает атрибуты объектов (жанры, режиссёр, актёры) с профилем, построенным по оценкам самого пользователя.
- **Рекомендации на основе знаний** (knowledge-based) подбирают объекты по явно заданным требованиям и правилам соответствия. История оценок не нужна [5].
- **Контекстно-зависимые** системы (context-aware) учитывают обстоятельства выбора: время, место, компанию [7].
- **Диалоговые** системы (conversational) уточняют потребность в многошаговом диалоге [8].
- **Системы на основе больших языковых моделей** (LLM-based) используют модель для понимания запроса, отбора кандидатов и формулировки объяснений [9, 10].
- **Гибридные** системы сочетают несколько подходов и компенсируют слабые стороны каждого [11].

Выбор подхода определяют три проблемы.

**Холодный старт.** У нового пользователя нет оценок, поэтому коллаборативные и контентные методы в первом сеансе неприменимы. Подходы на основе знаний и диалоговые работают сразу: требования пользователь сообщает сам.

**Галлюцинации.** Языковая модель, которая сама генерирует названия, может назвать несуществующий фильм или приписать реальному фильму неверные сведения. В исследованиях доля таких рекомендаций оценивается как отдельная метрика качества [3]. Защита — опора на поиск (retrieval grounding): модель выбирает из кандидатов, полученных из каталога, и не генерирует названия сама.

**Объяснимость.** Объяснения повышают прозрачность, доверие и удовлетворённость выбором [12, 13]. Объяснение полезно, только если оно отражает действительные причины выбора.

**Таблица 3.1 — Подходы к рекомендациям**

| Подход | Нужные данные | Холодный старт (К5) | Объяснимость (К4) | Решение |
|---|---|---|---|---|
| Коллаборативная фильтрация, матричная факторизация | Оценки многих пользователей | Не работает | Низкая | **Позже**: при появлении нескольких пользователей; для экспериментов — данные MovieLens [14] |
| Контентная фильтрация | Атрибуты фильмов, оценки пользователя | После первых оценок | Высокая | **Принято**: профиль предпочтений по оценкам |
| На основе знаний | Требования пользователя, атрибуты фильмов | Работает | Высокая | **Принято**: основной механизм отбора |
| Контекстно-зависимый | Контекст выбора | Зависит от базового метода | Средняя | **Принято**: время, компания, погода |
| Диалоговый | Диалог | Работает | Высокая | **Принято**: форма взаимодействия |
| Языковая модель сама называет фильмы | Запрос | Работает | Высокая, но непроверяемая | **Отклонено**: нарушает К3 |
| Языковая модель задаёт критерии, кандидаты берутся из каталога | Запрос и каталог | Работает | Высокая, проверяемая | **Принято** |

### 3.2. Подход CineMatch

CineMatch — гибридная система. Обработка запроса идёт в четыре шага:

1. Языковая модель извлекает из сообщения требования и контекст и формирует критерии поиска: жанры, годы, минимальный рейтинг, максимальную длительность.
2. Функция `find_movies` возвращает кандидатов из локального каталога и исключает просмотренные и уже предложенные фильмы.
3. Модель выбирает три фильма из возвращённых и объясняет выбор только по полям, полученным из каталога.
4. Код проверяет, что каждый предложенный фильм есть среди результатов поиска текущего хода.

Профиль предпочтений вычисляется из оценок пользователя при каждом обращении (ADR-013). Погода — слабый контекстный сигнал: она влияет на тон ответа и жанровый уклон, но не является жёстким фильтром.

## 4. ИИ-агенты

### 4.1. Понятие агента

Агент — система, которая воспринимает среду и действует в ней для достижения цели [15]. Среди систем на основе языковых моделей различают два класса [16]:

- **workflow** — модель и инструменты вызываются по путям, заданным в коде;
- **агент** — модель сама решает, какие инструменты вызывать и в каком порядке, получает результаты и продолжает работу до завершения задачи.

Агент на основе языковой модели состоит из модели, инструментов и инструкций [17].

**Вызов инструментов** (tool use, function calling) работает так. Разработчик описывает функции JSON-схемой, модель возвращает имя функции и аргументы, код выполняет функцию и передаёт результат модели. Цикл «рассуждение — действие — наблюдение» описан в работе ReAct [18]. Способность модели самой решать, когда обращаться к инструменту, исследована в работе Toolformer [19].

**Структурированный вывод** (structured output) ограничивает ответ модели заданной JSON-схемой. Он нужен там, где ответ обрабатывает код: при классификации запроса и извлечении параметров.

**Model Context Protocol** (MCP) — открытый протокол подключения инструментов и источников данных к приложениям на основе языковых моделей [20]. В MVP он не нужен, так как инструменты вызываются внутри одного процесса.

В проекте агентом называется компонент, в котором модель сама выбирает следующее действие и вызывает инструменты. Код, выполняющий заранее заданную последовательность шагов, агентом не считается.

### 4.2. Архитектурная схема

Обе методики, Anthropic и OpenAI, рекомендуют начинать с простейшей схемы и добавлять автономность там, где она даёт результат [16, 17]. Сначала следует использовать возможности одного агента. Работу делят между несколькими агентами, когда инструкции или набор инструментов становятся слишком сложными [17].

Несколько агентов без общего контекста принимают несогласованные решения [21]. Мультиагентные системы оправданы на задачах с независимыми подзадачами и расходуют примерно в 15 раз больше токенов, чем обычный чат [22]. В CineMatch всё, что сообщил пользователь (настроение, время, компания), нужно на каждом шаге, а инструментов десять и они не пересекаются.

**Таблица 4.1 — Варианты архитектуры**

| Вариант | Описание | Достоинства | Недостатки | Решение |
|---|---|---|---|---|
| Workflow без агента | Код задаёт шаги; модель только извлекает параметры и пишет текст | Предсказуемость | Агентности нет; каждый сценарий — отдельная ветка кода | **Отклонено** |
| Классификатор и три специализированных агента | Код направляет сообщение распознавателю состояния, рекомендателю или компаньону | Короткие промпты | Три промпта; лишний вызов модели на каждое сообщение; контекст теряется при переключении | **Отклонено** (первоначальный вариант) |
| Инварианты в коде и один агент с защитными механизмами | Код отвечает за согласие, город, удаление данных, лимиты и проверку ответа; агент сам выбирает инструменты | Общий контекст, одна трасса решений, наглядная агентность | Поведение менее предсказуемо, поэтому нужны защитные механизмы и тестовые диалоги | **Принято** |
| Автономный агент с ограничениями только в промпте | Согласие и удаление данных — инструменты агента | Минимум кода | Обязательные шаги зависят от решения модели; уязвимость к prompt injection | **Отклонено** |
| Мультиагентная система | Ведущий агент и субагенты | Параллельная обработка | Нет общего контекста; дорого; сложная отладка | **Отклонено** |

Принятая схема:

```
Код             согласие → город → этап сессии → лимиты
                │
                ▼
Классификатор   cinema / delete_data / off_topic / unsafe (структурированный вывод)
                │ cinema                  │ delete_data: подтверждение и удаление — только кодом
                ▼
Агент           сам выбирает инструменты:
                extract_context · get_user_ratings · get_user_profile · get_weather
                find_movies · get_movie_with_credits · search_movie
                save_choice · save_rating · close_choice
                │
                ▼
Код             проверка ответа: фильмы — из результатов find_movies этого хода; схема; длина
```

Распознавание состояния выполняет инструмент `extract_context`. Это отдельный вызов модели со структурированным выводом: настроение, свободное время, компания, пожелания. Основной агент сам решает, когда его вызвать. Специализация первоначального распознавателя состояния сохраняется без второго агента.

Решение зафиксировано в ADR-026 и отражено в документах модуля ИИ-агентов.

### 4.3. Защитные механизмы

Системный промпт задаёт поведение, но не гарантирует его. Модель может ошибиться или выполнить инструкцию, встроенную в данные (prompt injection). Один механизм защиты недостаточен, надёжность обеспечивает сочетание нескольких уровней [17]. Юридически значимые действия выполняет только код.

**Таблица 4.2 — Уровни защиты**

| Уровень | Механизм | Где реализуется |
|---|---|---|
| Инварианты | Согласие до первого обращения к модели; удаление данных только кодом и только после подтверждения; этапы сессии | Код оркестратора |
| Релевантность | Классификатор отсекает запросы не по теме и небезопасные; агент для них не вызывается | Отдельный вызов модели |
| Инструкции | Роль, тон, запрет называть фильмы не из результатов поиска | Системный промпт |
| Доступ к инструментам | Агенту доступны только перечисленные функции; удаления данных среди них нет; аргументы проверяются по схеме; `save_choice` принимает только фильм из последней подборки | Реестр инструментов |
| Проверка ответа | Каждый `movie_id` есть в результатах `find_movies` текущего хода; иначе повтор, затем сообщение об ошибке | Код |
| Лимиты | Не более 8 вызовов модели на сообщение; лимит токенов на сообщение; лимит расходов на ключ API | Фреймворк, RouterAI |
| Недоверенные данные | Описания фильмов передаются модели как данные, не как инструкции | Промпт, код |

### 5.2. Выбор модели

Модель выбирается по четырём критериям: надёжность вызова инструментов, качество русского языка, цена и скорость ответа. Ориентирами служат рейтинги BFCL для вызова функций [31] и MERA для русского языка [32]. Окончательный выбор делается по собственному тесту.

**Таблица 5.2 — Модели-кандидаты**

| Модель | Цена в RouterAI, ₽ за 1 млн токенов (вход / выход) | Решение |
|---|---|---|
| DeepSeek V4 Flash | 5,25 / 15 (провайдер по умолчанию; у других провайдеров цена выше) | **Принято** (предварительно) |
| Qwen3.8 Flash | 16 / 51 | **Резерв** |
| DeepSeek V4.1 Flash | ≈ 4 / 34 | **Позже**: выпущена в сентябре 2026 года, нужна проверка |
| Alice AI LLM (Яндекс) | 757 / 3019 | **Отклонено**: цена |
| Модели OpenAI, Anthropic, Google | В десятки раз дороже | **Отклонено**: цена |

На одно сообщение пользователя приходится 3–6 вызовов модели и 10–30 тыс. входных токенов. На DeepSeek V4 Flash это меньше 1 ₽.

Тест модели: 30 диалогов на русском языке. Оцениваются доля корректных вызовов инструментов, доля ответов, прошедших проверку схемы, и доля рекомендаций вне каталога (допустимое значение — 0). Методика теста фиксируется в ТЗ, результаты — в пояснительной записке.

### 11.4. Разработка от спецификации

Разработка от спецификации (spec-driven development) — подход, при котором до написания кода фиксируются требования, технический план и список задач. Код, в том числе сгенерированный ИИ-агентом, проверяется на соответствие этим документам.

GitHub Spec Kit [40] реализует подход набором команд для ИИ-агента программирования:

| Команда | Результат |
|---|---|
| `/speckit.constitution` | Принципы проекта |
| `/speckit.specify` | Спецификация функции: что и зачем |
| `/speckit.clarify` | Уточняющие вопросы по спецификации |
| `/speckit.plan` | Технический план: как |
| `/speckit.tasks` | Список задач |
| `/speckit.analyze` | Проверка согласованности документов |
| `/speckit.implement` | Реализация задач агентом |

**Таблица 11.4 — Подходы к спецификациям**

| Вариант | Особенности | Решение |
|---|---|---|
| PRD, ADR и AGENTS.md [41] | Короткие документы требований и решений; файл инструкций для ИИ-агентов в открытом формате | **Принято**: основа процесса |
| GitHub Spec Kit | MIT, версия 1.x; поддерживает OpenCode; генерирует объёмные документы на каждую функцию | **Принято**: для одной-двух ключевых функций (подбор фильма, удаление данных) |
| OpenSpec | Более лёгкий цикл: предложение изменения → задачи → архив | **Резерв** |
| Kiro | Собственная среда разработки AWS | **Отклонено** |
| Tessl | Коммерческая платформа | **Отклонено** |
| BMAD Method | Набор ролей-агентов: аналитик, менеджер, архитектор и др. | **Отклонено**: избыточный процесс |

Для каждой функции Spec Kit создаёт несколько объёмных документов. Применять его ко всем задачам команды из трёх человек избыточно, поэтому он используется только там, где спецификация служит демонстрационным артефактом проекта.

Термин «вайб-кодинг» (vibe coding) ввёл А. Карпати в феврале 2025 года [43]. Так называют разработку, при которой код генерирует модель по описанию на естественном языке, а разработчик не разбирает его построчно. В проекте генерация кода разрешена при соблюдении правил:

1. Спецификация пишется до кода.
2. Каждый pull request проходит ревью участником, который может объяснить код.
3. Инструменты агента покрываются тестами.
4. Ключи API и персональные данные не попадают в промпты и репозиторий.

## 14. Правовые требования

**Персональные данные.** Федеральный закон № 152-ФЗ [48] не распространяется на обработку персональных данных физическими лицами исключительно для личных и семейных нужд (ч. 2 ст. 1). Локальная установка у одного пользователя подпадает под это исключение: команда данные пользователя не получает.

Текст сообщений при этом передаётся через RouterAI провайдеру модели, сервер которого может находиться за рубежом [30]. Поэтому уже в MVP приняты меры, которые понадобятся в серверной версии:

1. Согласие перед началом работы содержит отдельный пункт о передаче текста сообщений внешним провайдерам языковых моделей, в том числе зарубежным.
2. В запросы к модели не передаются данные, позволяющие установить личность. Идентификатор пользователя используется только внутри серверной части, а история оценок передаётся как пары «фильм — оценка».
3. Все данные хранятся локально и удаляются по команде пользователя.

При развёртывании на сервере команда становится оператором персональных данных. Тогда нужны политика обработки и согласие (ст. 9), уведомление Роскомнадзора (ст. 22), хранение данных граждан России на территории России (ч. 5 ст. 18) и уведомление о трансграничной передаче (ст. 12).

**Возрастная маркировка.** Федеральный закон № 436-ФЗ [49] устанавливает категории 0+, 6+, 12+, 16+ и 18+. Каждая карточка фильма показывает возрастную маркировку (раздел 6.1).

## Будущий функционал

Решения со статусом «Позже»:

- коллаборативная фильтрация по оценкам нескольких пользователей и данным MovieLens;

- WebSocket для совместного выбора фильма компанией;
- локальные модели для работы без внешнего API;
- Telegram-бот как тонкий клиент к той же серверной части; образец функций напоминаний — Hermes Agent;
- MCP-сервер с инструментами CineMatch для подключения к другим агентам;
- Dev Containers для единой среды разработки.
