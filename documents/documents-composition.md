# CineMatch — состав проектной документации

Документ определяет, какие проектные документы ведутся в проекте CineMatch, что должно быть в каждом из них, кто за него отвечает и в какой нотации выполняются диаграммы. Состав построен по типовой структуре проектной документации (блоки A–I, разделы 010–165) и адаптирован к архитектуре проекта.

| | |
|---|---|
| Версия | 1.0 |
| Дата | 03.10.2026 |
| Связанные документы | [Vision проекта](../docs/vision/vision_project.md), vision модулей в [`docs/vision/`](../docs/vision/) |

## 1. Организация документации

### 1.1 Размещение

```
documents/
├── documents-composition.md   ← этот документ
├── agents.md                  ← модуль ИИ-агентов
├── data.md                    ← модуль данных
├── ui.md                      ← модуль интерфейса
├── diagrams/
│   ├── agents/                ← исходники PlantUML (.puml) и изображения (.svg)
│   ├── data/
│   └── ui/
└── prototype/
    └── index.html             ← live-прототип интерфейса (раздел 115 модуля интерфейса)
```

Каждый модуль ведёт один документ, содержащий все разделы 010–165 в установленном порядке. Номер раздела совпадает с номером в типовой структуре, что позволяет сопоставлять документы модулей между собой и с типовым составом.

### 1.2 Модули и ответственность

| Модуль | Документ | Состав модуля |
|---|---|---|
| ИИ-агенты | `agents.md` | Оркестратор диалога, классификатор намерений, агенты (распознаватель состояния, рекомендатель, компаньон, планировщик), клиент LLM, защита диалога |
| Данные | `data.md` | База данных SQLite, загрузка каталога из TMDB, сервис погоды Open-Meteo, функции-инструменты и служебные функции |
| Интерфейс | `ui.md` | Консольное приложение, Telegram-бот, планировщик отправки напоминаний, администрирование бота |

Ответственный за модуль является автором своего документа. Изменения в документе любого модуля вносятся через pull request; изменения, затрагивающие контракты между модулями (разделы 130, 135, 140), требуют одобрения ответственных за все три модуля.

### 1.3 Системные и модульные артефакты

Часть артефактов описывает систему целиком, часть — отдельный модуль. Чтобы не дублировать их и не допускать расхождений, установлены следующие правила.

| Артефакт | Уровень | Нумерация | Где определяется |
|---|---|---|---|
| Акторы | системный | — | Определяются в `agents.md`, раздел 030; документы других модулей ссылаются на них и дополняют своими внутренними системами |
| Вариант использования | системный | `UC-1`, `UC-2`, … (сквозная) | Вводится в документе модуля, который отвечает за основную логику сценария; остальные модули описывают свою часть со ссылкой на номер |
| Пользовательская история | системный | `US-01`, `US-02`, … (сквозная) | Аналогично вариантам использования |
| Эпик | системный | `EP-1`, `EP-2`, … (сквозная) | `agents.md`, раздел 090; модули указывают, какие эпики затрагивают |
| Архитектурное решение | системный | `ADR-001`, … (сквозная) | В документе модуля, к которому решение относится; номер берётся следующий свободный по всему проекту |
| Событие | системный | имя на английском в прошедшем времени, например `RatingSaved` | Модуль-издатель события |
| Функциональное требование | модульный | `FR-AG-01`, `FR-DB-01`, `FR-UI-01` | Документ модуля |
| Нефункциональное требование | модульный | `NFR-AG-01`, `NFR-DB-01`, `NFR-UI-01` | Документ модуля |
| Тестовый сценарий | модульный | `TS-AG-01`, `TS-DB-01`, `TS-UI-01` | Документ модуля, раздел 095 |

### 1.4 Нотация диаграмм

Диаграммы выполняются в нотации **UML 2.x**. Исходный текст пишется на PlantUML и хранится в репозитории рядом с изображением в формате SVG; в документ вставляется изображение. Такой способ обеспечивает корректное отображение на GitHub и возможность править диаграммы через pull request.

| Раздел | Диаграмма UML |
|---|---|
| 020 System Context | Диаграмма компонентов (уровень системы) |
| 050 Entities + Lifecycle | Диаграмма классов; диаграмма состояний |
| 060 Use Cases | Диаграмма вариантов использования |
| 120 Data Model | Диаграмма классов (логическая модель) или ER-диаграмма |
| 146 Logic Scheme | Диаграмма деятельности |
| 150 Component Diagram | Диаграмма компонентов (уровень модуля) |
| 155 Sequence-диаграммы | Диаграмма последовательности |
| 165 Deployment Diagram | Диаграмма развёртывания |

Имя файла диаграммы: `<номер раздела>-<содержание>.puml`, например `155-seq-recommend.puml`.

### 1.5 Правила оформления

1. Язык документов — русский; термины при первом упоминании сопровождаются английским эквивалентом, имена в коде (функции, поля, события) — на английском.
2. Каждый документ начинается с таблицы: модуль, версия, дата, связанные документы.
3. Решения, не подтверждённые командой, помечаются статусом «предложено»; допущения выносятся в раздел «Допущения и открытые вопросы» в конце документа.
4. Если раздел к модулю неприменим, он не удаляется: в нём указывается, чем он заменён или почему не требуется.
5. Требования формулируются проверяемо: для нефункциональных требований обязательны метрика и пороговое значение.

### 1.6 Порядок подготовки

| Этап | Разделы | Результат |
|---|---|---|
| 1 | Блоки A–C (010–090) | Границы, предметная область, требования |
| 2 | Блок D (095) | Проверка полноты требований |
| 3 | Блоки E–G (110–140) | Диалог и интерфейсы, данные, контракты |
| 4 | Блоки H–I (145–165) | Архитектура, интеграция, развёртывание |
| 5 | — | Техническое задание формируется на основе документов модулей |

Документы являются исходными спецификациями для разработки по методологии spec-driven development (GitHub Spec Kit): из них формируются спецификации, план и задачи для ИИ-агента программирования.

## 2. Состав документов

### Блок A. Контекст и границы системы

#### 010 — Глоссарий (Glossary)

**Назначение.** Установить единую терминологию проекта и модуля, исключить разночтения в названиях сущностей, процессов и ролей.

**Содержание:**
- таблица: термин, английский эквивалент, определение, где используется;
- термины предметной области модуля (рекомендации, диалог, агенты, каталог), а не общепрограммные понятия;
- ссылки на совпадающие термины в документах других модулей; одинаковые термины во всех документах имеют одинаковые определения.

**По модулям:** агенты — понятия агентного подхода и диалога (агент, инструмент, намерение, вектор состояния, подборка); данные — понятия каталога и хранения (каталог, профиль предпочтений, возрастная маркировка, сессия хранения); интерфейс — понятия взаимодействия (быстрый ответ, команда бота, уведомление).

#### 020 — System Context

**Назначение.** Определить границы модуля: что в него входит, что остаётся за его пределами, с какими системами и акторами он взаимодействует.

**Содержание:**
- диаграмма контекста (UML, диаграмма компонентов): модуль в центре, смежные модули и внешние системы вокруг;
- для каждой внешней системы: название, роль по отношению к модулю, тип интеграции;
- явный перечень того, что входит и не входит в модуль.

**Внешние системы проекта:** TMDB API, Open-Meteo API, OpenRouter (LLM API), Telegram Bot API.

#### 030 — Actors

**Назначение.** Зафиксировать всех участников взаимодействия — людей и системы.

**Содержание:**
- таблица: актор, тип (человек, внутренняя система, внешняя система), описание, цели в системе;
- для людей — роль и действия в системе: пользователь консоли, пользователь Telegram, администратор;
- для систем — протокол и сценарий интеграции.

### Блок B. Анализ предметной области

#### 040 — Event Storming

**Назначение.** Смоделировать процессы через доменные события и команды; основа для выделения сущностей.

**Содержание:**
- таблица событий в порядке процесса: команда (и её инициатор), доменное событие в прошедшем времени, агрегат, обработчик;
- события охватывают полный цикл: согласие на обработку данных → подбор → выбор → напоминание → оценка, а также напоминания, подписки и удаление данных.

#### 050 — Entities + Lifecycle

**Назначение.** Выделить ключевые сущности и описать их жизненный цикл.

**Содержание:**
- диаграмма классов UML: сущности, атрибуты с типами и ограничениями, связи с кратностями;
- таблица сущностей: атрибуты, связи, ограничения;
- диаграммы состояний UML для сущностей со статусами; для каждого состояния — описание и триггеры переходов.

**По модулям:** агенты — сессия диалога (этапы диалога), подборка, напоминание; данные — физические сущности каталога и пользователя, жизненный цикл записей (создание, обновление, удаление по сроку и по запросу пользователя); интерфейс — состояния сообщений и кнопок (например, неактуальная подборка после выбора).

#### 060 — Use Cases

**Назначение.** Описать функциональные требования через варианты использования; связать акторов и сценарии.

**Содержание:**
- диаграмма вариантов использования UML с отношениями `<<include>>` и `<<extend>>`;
- перечень вариантов использования: номер, название, актор, интерфейс (консоль, бот), этап реализации;
- спецификации ключевых вариантов: актор, предусловия, постусловия, основной поток, альтернативные потоки, связанные истории.

### Блок C. Требования и роли

#### 070 — RBAC (Role-Based Access Control)

**Назначение.** Определить роли и их права на действия и данные.

**Содержание:**
- матрица «роль × действие» для ролей: пользователь консоли, пользователь Telegram, администратор;
- соответствие ролей акторам из раздела 030 и способ определения роли (администраторы — по списку Telegram ID в конфигурации);
- для модуля агентов дополнительно — матрица «агент × инструмент» (принцип минимальных прав): какие инструменты модель каждого агента может вызывать.

#### 075 — NFR (Non-Functional Requirements)

**Назначение.** Зафиксировать нефункциональные требования — ограничения и атрибуты качества.

**Содержание:**
- требования по категориям: производительность, надёжность, безопасность, приватность, стоимость, сопровождаемость, наблюдаемость;
- для каждого требования — измеримая метрика и пороговое значение;
- связь с архитектурными решениями (145) и тестовыми сценариями (095).

#### 080 — User Stories

**Назначение.** Описать потребности пользователей в формате, пригодном для разработки и проверки.

**Содержание:**
- истории в формате «Как ‹актор›, я хочу ‹действие›, чтобы ‹ценность›»;
- критерии приёмки в формате Given — When — Then, несколько сценариев на историю;
- группировка по акторам;
- ссылки на варианты использования (060) и роли (070).

#### 090 — Epics / Features

**Назначение.** Сгруппировать истории в крупные функциональные блоки для планирования.

**Содержание:**
- перечень эпиков: название, описание, приоритет по MoSCoW;
- связанные истории;
- веха дорожной карты, к которой эпик реализуется: MVP (консоль), Telegram-бот, заморозка функций.

### Блок D. Верификация

#### 095 — Traceability Matrix

**Назначение.** Проверить полноту покрытия: каждое требование связано с историей, документом и способом проверки.

**Содержание:**
- матрица: требование, тип (ФТ, НФТ, интеграционное), источник (vision, решение команды), вариант использования, история, разделы документа, тестовый сценарий, статус (`covered`, `partial`, `missing`);
- перечень тестовых сценариев `TS-…` с кратким описанием проверки;
- вывод о пропусках и непокрытых требованиях.

Матрица перепроверяется с помощью ИИ-ассистента после каждого существенного изменения документов.

### Блок E. Проектирование интерфейсов

#### 110 — UI/UX

**Назначение.** Спроектировать взаимодействие с пользователем до начала разработки.

**Содержание:**
- принципы: консистентность, обратная связь на каждое действие, предсказуемость, минимизация когнитивной нагрузки, доступность;
- описание ключевых экранов и сообщений: структура, элементы, состояния (ожидание, пустой результат, ошибка);
- навигация и переходы между экранами и сообщениями;
- видимость элементов в зависимости от роли и интерфейса;
- привязка экранов к вариантам использования и историям;
- подтверждение необратимых действий (удаление данных).

**По модулям:** интерфейс — экраны консоли, сообщения и кнопки бота; агенты — диалоговый дизайн: типы ответов, фиксированные вопросы, тон и формулировки, сообщения об ошибках и отказах; данные — не применяется, раздел содержит ссылку на документы других модулей.

#### 115 — Live-прототип

**Назначение.** Проверить сценарии взаимодействия до реализации.

**Содержание:**
- интерфейс — интерактивный HTML-прототип (один `index.html` с навигацией по экранам консоли и чата бота) и описание сценариев;
- агенты — эталонные диалоги по основным сценариям, используемые для проверки промптов и тестовых сценариев;
- данные — не применяется.

### Блок F. Проектирование данных

#### 120 — Data Model

**Назначение.** Спроектировать структуру данных — основу для схемы БД и контрактов.

**Содержание:**
- модуль данных — диаграмма логической модели (UML-классы или ER), описание каждой таблицы (столбец, тип, ограничения NOT NULL, UNIQUE, FK, смысл поля), индексы, связи и каскадное удаление, сроки хранения, удаление данных пользователя по запросу;
- модуль агентов — структуры, которые модуль создаёт и передаёт (состояние сессии, вектор состояния, намерение), с типами и допустимыми значениями; указание, где каждая структура хранится;
- модуль интерфейса — данные, которые интерфейс хранит сам (если хранит), иначе указание на их отсутствие;
- согласованность с сущностями раздела 050.

### Блок G. Контракты и события

#### 130 — API Contracts

**Назначение.** Специфицировать контракты синхронного взаимодействия между модулями и с внешними системами.

**Адаптация.** Модули работают в одном процессе Python и взаимодействуют вызовами функций; REST API между модулями отсутствует. Контракт описывается как сигнатуры функций и JSON Schema передаваемых структур вместо OpenAPI.

**Содержание:**
- сигнатуры функций: параметры, типы, результат, коды ошибок;
- JSON Schema структур, примеры успешного и ошибочного результата;
- для модуля агентов — схемы инструментов в формате tool calling и разделение параметров на передаваемые моделью и подставляемые кодом;
- для модуля данных — используемые запросы к TMDB и Open-Meteo;
- для модуля интерфейса — использование Telegram Bot API;
- версия контракта по semver.

#### 135 — Event Catalog

**Назначение.** Перечень событий: кто их создаёт, кто обрабатывает, при каких условиях.

**Адаптация.** Брокер сообщений в проекте не используется. События фиксируются записями в БД (например, напоминания) и в журнале; асинхронная доставка реализована опросом таблицы напоминаний планировщиком отправки.

**Содержание:**
- таблица: событие, издатель, обработчики, триггер, критичность;
- краткое описание смысла каждого события.

#### 140 — Event Schema

**Назначение.** Спецификация структуры каждого события.

**Содержание:**
- общие поля события (`event`, `schema_version`, `event_id`, `user_id`, `occurred_at`) и поля данных для каждого события: имя, тип, обязательность, допустимые значения;
- порядок событий одного пользователя — по `occurred_at`; ключ разбиения не требуется ввиду отсутствия брокера;
- правила совместимости: поля только добавляются, версия указывается в `schema_version`.

### Блок H. Архитектура и логика

#### 145 — ADR (Architecture Decision Records)

**Назначение.** Фиксировать значимые архитектурные решения, их контекст и последствия.

**Содержание:**
- решения по шаблону: контекст → решение → последствия (положительные и отрицательные);
- статус каждого решения (принято, предложено, отменено);
- связь решений с нефункциональными требованиями (075).

Журнал решений команды (`docs/decisions.md`) переносится в раздел 145 соответствующего модуля.

#### 146 — Logic Scheme

**Назначение.** Показать логику работы модуля — потоки управления и данных без привязки к развёртыванию.

**Содержание:**
- диаграмма деятельности UML для основного процесса модуля (для агентов — обработка одного сообщения; для данных — загрузка каталога и поиск кандидатов; для интерфейса — обработка ввода и отображение ответа);
- описание потоков данных; указание синхронных и асинхронных взаимодействий;
- границы модуля и внешние зависимости.

#### 150 — Component Diagram

**Назначение.** Показать, из каких компонентов состоит модуль и как они связаны.

**Содержание:**
- диаграмма компонентов UML;

### Блок I. Интеграции и развёртывание

#### 155 — Sequence-диаграммы

**Назначение.** Детализировать ключевые сценарии взаимодействия.

**Содержание:**
- диаграммы последовательности UML для ключевых сценариев модуля;
- для каждого сценария: участники, сообщения, таймауты, обработка ошибок и альтернативные ветви (фрагменты `alt`, `opt`);
- привязка к вариантам использования, историям и контрактам (130).

#### 160 — Integration Plan

**Назначение.** План стыковки модуля с другими модулями и внешними системами.

**Содержание:**
- перечень интеграций: с кем, тип взаимодействия;
- порядок реализации: контракты → заглушки → реальные реализации → сквозные сценарии;
- сроки по дорожной карте проекта;
- критерии готовности каждой интеграции.

#### 165 — Deployment Diagram

**Назначение.** Описать физическое размещение системы.

**Содержание:**
- диаграмма развёртывания UML: узлы, артефакты, внешние системы, протоколы;
- окружения: разработка (компьютеры участников), рабочее (сервер — на этапе Telegram-бота);
- требования к серверу: процессор, память, диск, ОС, сетевой доступ;
- соответствие компонентов (150) узлам развёртывания.
