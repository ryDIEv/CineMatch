# 145 — ADR

*CineMatch. Модуль данных* | [оглавление модуля](README.md)

Нумерация сквозная по проекту; полный порядок — в [145 модуля агентов](../agents/145.architecture-decisions.md). Здесь — ADR-011…ADR-018, ADR-029, ADR-041 и ADR-042; решения ADR-030…ADR-040 общие для всех модулей и обязательны к исполнению.

### ADR-011

**SQLite, один файл, режим WAL.** *Принято.*

Контекст: один пользователь, локальный запуск, команда без опыта администрирования СУБД; при этом чтение должно работать во время загрузки каталога.

Решение: SQLite в томе Docker, файл `cinematch.db`; `journal_mode = WAL`, `foreign_keys = ON`, `busy_timeout = 5000`, `synchronous = NORMAL`; параметры задаются на каждом соединении в `cinematch/data/db.py` ([120 §1](120.data-model.md#1-файл-базы-и-параметры-подключения)).

Последствия: (+) нет отдельного сервера базы, резервное копирование — копирование файла, чтение не блокируется загрузкой; (−) одна запись в момент времени, при нескольких пользователях или нескольких процессах-писателях потребуется PostgreSQL.

### ADR-012

**Каталог — TMDB API.** *Принято.*

Контекст: Кинопоиск и Netflix не дают открытого API; нужны жанры, актёры, постеры и данные на русском.

Решение: TMDB с бесплатным ключом (`TMDB_API_KEY`), язык `ru-RU`, запросы по [130 §7.1](130.api-contracts.md#71-запросы-к-tmdb); атрибуция TMDB в интерфейсе и README (NFR-DB-13). Каталог — локальная копия: во время диалога TMDB не вызывается.

Последствия: (+) полные метаданные и постеры, один источник; (−) регистрация ключа, зависимость от доступности и условий TMDB, необходимость загрузки перед первым запуском.

### ADR-013

**Профиль рассчитывается при чтении.** *Принято, уточнено 09.11.2026.*

Контекст: профиль нужен агенту при каждом подборе, а оценки меняются после каждого хода; отдельная таблица профиля рассинхронизировалась бы с `user_ratings`.

Решение: профиль считается функцией `get_user_profile` по всем оценкам пользователя; таблицы нет.

Нормированная оценка фильма: `r = (rating − 5.5) / 4.5`, где `rating` — целое 1…10; `r ∈ [−1, 1]`, нейтральная оценка 5,5 даёт 0.

Вес жанра `g`:

```
raw_g   = Σ r_i / n_g                      (по оценённым фильмам с жанром g)
c_g     = n_g / (n_g + 3)                  (доверие к выборке)
weight_g = round(raw_g × c_g, 3)           (в пределах [−1, 1])
```

`n_g` — число оценённых фильмов жанра. Жанр без оценок в `genre_weights` не попадает (не `0`). Множитель `c_g` не даёт одной оценке дать вес ±1: при `n = 1` вес равен четверти `raw`, при `n = 10` — 77 % `raw`.

Вес актёра — та же формула, где `n_a` — число оценённых фильмов, в которых актёр входит в первые 10 (`movie_cast.billing_order`). В `actor_weights` попадают до 20 актёров с наибольшим `|weight|`; при равенстве — по имени.

Пример на пяти оценках:

| Фильм | Оценка | `r` | Жанры |
|---|---|---|---|
| A | 9 | 0,778 | драма, комедия |
| B | 7 | 0,333 | драма |
| C | 4 | −0,333 | комедия, ужасы |
| D | 10 | 1,000 | драма |
| E | 2 | −0,778 | ужасы |

| Жанр | `n_g` | `raw_g` | `c_g` | `weight_g` |
|---|---|---|---|---|
| драма | 3 | (0,778 + 0,333 + 1,000) / 3 = 0,704 | 3 / 6 = 0,50 | 0,352 |
| комедия | 2 | (0,778 − 0,333) / 2 = 0,222 | 2 / 5 = 0,40 | 0,089 |
| ужасы | 2 | (−0,333 − 0,778) / 2 = −0,556 | 0,40 | −0,222 |

Результат: `{"genre_weights": {"драма": 0.352, "комедия": 0.089, "ужасы": -0.222}, "actor_weights": {...}, "ratings_count": 5}`.

Правила:

1. Профиль считается по всем оценкам; `limit` в `get_user_ratings` ограничивает только выдачу модели.
2. Холодный старт — пустые словари, `ratings_count = 0`; агент в этом случае опирается на слова пользователя, а не на профиль.
3. `mood_match` в формулу не входит: это признак попадания в настроение, а не оценка фильма. Учитывать его — будущий функционал.
4. Профиль не влияет на SQL `find_movies`: веса использует агент, выбирая жанры для запроса (ADR-036).
5. Порядок ключей в ответе фиксирован: по убыванию `|weight|`, затем по названию — иначе результат невоспроизводим.

Последствия: (+) нет рассинхронизации, оценка сразу меняет профиль; (−) расчёт при каждом запросе — при сотнях оценок это единицы миллисекунд (NFR-DB-02).

### ADR-014

**Погода — Open-Meteo с кэшем 30 минут.** *Принято, уточнено 09.11.2026.*

Решение: координаты города сохраняются при онбординге (`users.latitude`, `users.longitude`); погода запрашивается по координатам, кэшируется в памяти процесса на 30 минут (ключ — координаты, округлённые до 3 знаков); тайм-аут 3 с; отказ сервиса — `None` без кэширования и без ошибки пользователю ([130 §8](130.api-contracts.md#8-погода-и-геокодирование)).

Последствия: (+) бесплатно, без регистрации, погода не задерживает ход; (−) только некоммерческое использование (условия Open-Meteo), кэш теряется при перезапуске.

### ADR-015

**Проверка параметров инструментов в модуле данных.** *Принято.*

Контекст: параметры приходят от модели, которая может ошибиться или быть обманута текстом пользователя.

Решение: каждый параметр проверяется по типу и диапазону до построения запроса ([130 §4](130.api-contracts.md#4-описание-функций)); SQL — только через SQLAlchemy с подстановкой параметров; ошибка возвращается модели как `ToolError` с кодом из [contracts §6](../overall/contracts.md#6-ошибки).

Последствия: (+) защита от ошибок модели и внедрения SQL; (−) дублирование границ в JSON Schema инструмента и в проверке — расхождение ловится тестом TS-DB-04.

### ADR-016

**Удаление через каскадные внешние ключи.** *Принято.*

Решение: все пользовательские таблицы (`user_ratings`, `user_choices`, `sessions`) ссылаются на `users` с `ON DELETE CASCADE`; `PRAGMA foreign_keys = ON` на каждом соединении; удаление — одна транзакция, предварительный подсчёт строк для отчёта ([120 §10](120.data-model.md#10-хранение-и-удаление)).

Последствия: (+) полное удаление одним запросом, ни одна таблица не забыта; (−) при выключенных внешних ключах каскад молча не работает — проверяется TS-DB-08.

### ADR-017

**Идентификатор пользователя с префиксом источника.** *Принято.*

Решение: `user_id = "<source>:<id>"`; в MVP `web:local` (`CINEMATCH_USER_ID`); в будущем `web:<id>`, `tg:<id>`. Столбец `users.source` хранит источник отдельно и в MVP допускает только `web`.

Последствия: (+) готовность к нескольким пользователям и интерфейсам без изменения схемы; (−) `source` и `user_id` нужно проверять на согласованность при появлении второго источника.

### ADR-018

**Возрастная маркировка из TMDB `release_dates`.** *Принято 09.11.2026.*

Контекст: в `movie/{id}` маркировки нет; она лежит в `release_dates.results[]`, по стране, и заполнена не у всех фильмов.

Решение: маркировка берётся из ответа `append_to_response=release_dates` по правилу:

1. Блок `results[]` с `iso_3166_1 = "RU"`: из его `release_dates[]` берётся первая непустая `certification` в порядке `type` 3 (кинотеатр), 4 (цифра), 5 (носитель), 6 (ТВ), 1 (премьера).
2. Если блок `RU` пуст или все `certification` пусты — блок `US`, преобразование по таблице ниже.
3. Если пусты оба — `NULL`; фильм остаётся в каталоге.
4. Если `adult = true` — `18+` независимо от сертификатов (`include_adult=false` в загрузке делает этот случай редким).

Преобразование `US → RU`:

| `certification` US | `age_rating` |
|---|---|
| `G` | `0+` |
| `PG` | `6+` |
| `PG-13` | `12+` |
| `R` | `16+` |
| `NC-17` | `18+` |
| пусто, `NR`, `UR`, `TV-*` | `NULL` |

Значения `RU` нормализуются: обрезка пробелов, `0+`, `6+`, `12+`, `16+`, `18+`; иное значение (например, `12` без плюса) приводится к ближайшему из перечня, при невозможности — `NULL`.

Правило пустой сертификации: `NULL` означает «маркировка не определена», а не «без ограничений». Агент не фильтрует такие фильмы по возрасту и не утверждает, что фильм разрешён детям; при `company = family` предпочтение отдаётся фильмам с маркировкой не выше `12+`, а `NULL` допустим только при отсутствии альтернатив ([120 агентов §2](../agents/120.data-model.md#2-правила-контекст--критерии-поиска)).

Последствия: (+) маркировка у большинства фильмов, правило воспроизводимо; (−) преобразование `US → RU` приблизительное и не заменяет российское прокатное удостоверение.

### ADR-029

**Доступ к базе через SQLAlchemy 2.0, миграции Alembic.** *Принято.*

Контекст: схема будет меняться; в будущем возможен переход на PostgreSQL.

Решение: SQLAlchemy 2.0 (ORM-модели в `cinematch/data/models.py`, запросы в `cinematch/data/repositories/`) и Alembic для миграций; параметры SQLite задаются при подключении; `alembic upgrade head` выполняется при старте backend и перед загрузкой каталога.

Последствия: (+) переход на PostgreSQL без переписывания запросов, история изменений схемы; (−) дополнительная библиотека, запрет на SQLite-специфичный SQL вне `db.py`.

### ADR-041

**Объём каталога MVP и порог голосов.** *Принято 09.11.2026.*

Контекст: в документах было три версии объёма (1 000, 5 000–10 000, 100 000 фильмов), а порог голосов не был зафиксирован; по ним нельзя ни загрузить каталог, ни проверить NFR.

Решение: каталог MVP — до **10 000** фильмов (500 страниц `discover` по 20 — предел пагинации TMDB); порог голосов — **100** в загрузке (`vote_count.gte`) и в выдаче `find_movies`; годы — с 1970. Значения совпадают с умолчаниями `scripts/load_catalog` ([110](110.ui-ux.md)).

Последствия: (+) одно число в требованиях, загрузке и тестах; 10 000 достаточно для подбора при пороге 100 голосов; (−) полная загрузка — около 10 500 запросов к TMDB, 5–10 минут при 40 запросах/с; фильмы до 1970 года в каталог не попадают; каталог не покрывает редкое кино.

Требование NFR-DB-01 «≤ 50 мс на 100 000 фильмов» остаётся требованием к запасу производительности и проверяется на синтетическом наборе, а не на боевом каталоге.

### ADR-042

**Заглушки каталога в поставку не входят.** *Принято 09.11.2026.*

Контекст: до реальной загрузки backend стартует с пустым каталогом, и агент не может подобрать фильм; обсуждался seed-набор «демо-фильмов».

Решение: каталог наполняется только загрузкой из TMDB; пустая база — допустимое состояние (`/health` → `catalog_size: 0`, подбор → `CATALOG_EMPTY`). Для тестов используется фикстура `tests/fixtures/seed_movies.json` (23 фильма), которая вставляется напрямую в тестовую базу; в образ и в том данных она не попадает. Состав фикстуры: разные жанры и длительность, не меньше одного фильма длиннее 150 минут, один ужастик, один фильм без возрастной маркировки, фильм с 42 голосами (порог 100), фильм с `runtime = NULL` (`max_runtime`), фильм с `overview` и `actors` и фильм, в `overview` которого спрятана инструкция (косвенное внедрение).

Последствия: (+) нет выдуманных фильмов в интерфейсе и расхождения между демо и реальными данными; тесты не зависят от сети; (−) демонстрация требует однократной загрузки каталога.
