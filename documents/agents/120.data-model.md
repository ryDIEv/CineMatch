# 120 — Data Model: структуры модуля

*CineMatch. Модуль ИИ-агентов* | [оглавление модуля](README.md)

Структуры модуля (`EveningContext`, `SessionState`, `AgentOutput`, `AgentTrace`, `RequestClass`) определены в [общем контракте](../overall/contracts.md#2-модели) — здесь они не дублируются. Этот документ описывает, как модуль ими пользуется: правила решений, жизненный цикл сессии, проверку ответа и детерминизм.

Физическую модель (таблицы) описывает [модуль данных](../data/120.data-model.md).

## 1. Что модуль создаёт и хранит

| Структура | Создаёт | Хранит | Ссылка |
|---|---|---|---|
| `EveningContext` | инструмент `extract_context` | в `SessionState.context` последним значением | [contracts §2.4](../overall/contracts.md#24-eveningcontext--контекст-вечера) |
| `SessionState` | оркестратор | JSON в таблице сессий, 24 ч без активности | [contracts §2.5](../overall/contracts.md#25-sessionstate--состояние-диалога) |
| `AgentOutput` | агент | не хранится, склеивается в `AgentResponse` | [contracts §2.6](../overall/contracts.md#26-agentoutput--структурированный-ответ-агента) |
| `AgentTrace` | код (по вызовам агента) | в ответе, в журнале | [contracts §2.7](../overall/contracts.md#27-agenttrace--шаг-трассы) |
| `RequestClass` | классификатор | не хранится, учитывается в журнале | [contracts §2.8](../overall/contracts.md#28-requestclass--класс-запроса) |

Правило: `movie_ids` и `reasons` агент возвращает раздельно; склейку с `MovieCard` из результата `find_movies` текущего хода выполняет оркестратор ([contracts §2.2](../overall/contracts.md#22-recommendedmovie--карточка-в-подборке)).

## 2. Правила «контекст → критерии поиска»

Приоритет: явное пожелание пользователя > правило по умолчанию. Правила применяет агент, а не код: они записаны здесь, чтобы один и тот же контекст давал один и тот же вызов `find_movies`.

| Контекст | Параметр `find_movies` | Правило |
|---|---|---|
| `available_minutes` задано | `max_runtime = available_minutes` | жёстко; фильм длиннее не показывается |
| `genre_wishes` не пуст | `genres = genre_wishes` | названия из справочника; неизвестный жанр не передаётся |
| `genre_wishes` пуст | `genres` не передаётся | поиск без жанрового фильтра |
| `genre_avoid` не пуст | параметра нет | агент не выбирает такие фильмы из выдачи; если вся выдача под запретом — ослабление или честный отказ |
| `year_from` / `year_to` из слов («новинки», «из девяностых») | `year_from`, `year_to` | только если пользователь назвал период явно |
| «проверенное», «с высоким рейтингом» | `min_rating` | значение передаёт агент; иначе параметр не передаётся и действует значение модуля данных |
| `mood = tired`, `energy = low` | без отдельных параметров | предпочтение комедии и драмы, длительность не выше указанной; хоррор и триллер — только по явной просьбе |
| `company = family` | без отдельных параметров | предпочтение семейного кино и возрастной маркировки не выше 12+; ужасы и триллеры не предлагаются |
| `company = friends` | без отдельных параметров | предпочтение комедий и приключений |
| Погода: дождь, холод | без отдельных параметров | уклон в спокойное и тёплое кино; погода — подсказка тона, не фильтр (ADR-036) |
| Погода недоступна | — | блок погоды в ответе не упоминается |
| Пользователь просит «посмешнее» после подборки | `genres = комедия` или уточнение к прежним | новые критерии заменяют прежние, показанное исключается кодом |

### 2.1. Ослабление критериев

Если `find_movies` вернул меньше трёх фильмов, допускается не больше двух ослаблений по порядку:

1. Убрать годовые рамки и `min_rating` (оставить жанры и длительность).
2. Убрать `genre_wishes`; `genre_avoid` остаётся.

`max_runtime` не ослабляется никогда: свободное время — жёсткое ограничение (§2, строка `available_minutes`).

После двух ослаблений, если фильмов всё равно нет: ответ без карточек, честное «по этим критериям ничего не нашлось» и предложение изменить пожелания. Выдумывать фильмы и показывать меньше трёх без объяснения нельзя.

Ослабление фиксируется в `AgentTrace`: шаг «Поиск», действие с новыми параметрами и результат «найдено N».

## 3. Сессия и восстановление

Сессия живёт 24 часа без активности; каждое сохранение продлевает срок. Источник истины по неоценённому выбору — таблица выборов, `SessionState.pending` — кэш.

Алгоритм начала хода:

```
user = get_user(user_id)
если user нет или user.consent_at пуст   → этап consent
иначе если user.city пуст                → этап onboarding
иначе                                     → этап dialog
если этап consent                          → сессия не читается и не создаётся:
                                             users ещё нет, этап выводится из user
сессия = get_session_state(user_id)
если сессии нет                           → создать с этапом по правилу выше
если этап confirm_delete и сессии нет     → этап dialog (подтверждение не восстанавливается)
если этап dialog                          → pending = get_pending_feedback(user_id)
```

Правила:

1. `/start` не создаёт запись в `messages`; создание сессии происходит при первом обычном сообщении после согласия: до него строки `users` нет, а `sessions.user_id` — внешний ключ ([120 данных §6](../data/120.data-model.md#6-sessions)).
2. `pending` заполняется из `get_pending_feedback`; при расхождении с кэшем побеждает база.
3. Если пользователь ушёл на этапе `confirm_delete`, сессия истекает, и следующий визит ведёт себя как обычный: удаление не выполняется.
4. `shown_ids` — до 50 последних; при переполнении вытесняются самые старые, иначе подбор «заканчивается» раньше времени.
5. `clarifications_asked` сбрасывается в 0 после показа подборки.
6. Удаление данных очищает сессию, выборы, оценки и настройки; следующий визит начинается с `consent`.

## 4. Классификатор по этапам

| Этап | Промпт | Значения | Что делает оркестратор |
|---|---|---|---|
| `consent` | `confirm_yes_no.md` | `yes`, `no` | `yes` → `set_consent(user_id, True)`; `no` → правила снова, ничего не сохраняется |
| `onboarding` | не вызывается | — | город разбирает `resolve_city` |
| `dialog` | `classifier.md` | `cinema`, `delete_data`, `off_topic`, `unsafe` | `cinema` → агент; `delete_data` → этап `confirm_delete`; остальные → отказ без агента |
| `confirm_delete` | `confirm_yes_no.md` | `yes`, `no` | `yes` → `delete_user_data`; `no` → этап `dialog` |

Ошибка классификатора: один повтор с тем же промптом; после второй ошибки — `cinema` не вызывается, пользователь получает отказ по теме; событие `GuardrailTriggered(rule=limit)` в журнал.

## 5. Проверка ответа

Порядок проверок после ответа агента:

1. Схема `AgentOutput` (Pydantic) — иначе повтор с `retry_invalid_output.md`.
2. Все `movie_id` есть в результате `find_movies` текущего хода — иначе повтор, затем `LLM_INVALID_OUTPUT`.
3. Длина `text` ≤ 1200 и каждого `reason` ≤ 240 — иначе повтор, затем `LLM_INVALID_OUTPUT`.
4. Число фильмов: ровно 3, если поиск вернул не меньше трёх; иначе — сколько вернул поиск ([contracts §5](../overall/contracts.md#5-сколько-фильмов-в-ответе)).
5. В `kind = question` не больше одного вопроса в тексте.

Повторов не больше одного на ход; второй невалидный ответ пользователю не показывается.

## 6. Детерминизм

| Что | Значение | Почему |
|---|---|---|
| Температура агента | 0.3 | воспроизводимость эталонных диалогов при живом тоне |
| Температура классификатора и `extract_context` | 0 | один и тот же вход — один и тот же класс и контекст |
| Вызовов модели на сообщение | ≤ 8 | NFR-AG-10 |
| Повторов запроса к модели | 1 | NFR-AG-04 |
| Потоковая передача токенов | нет | потоковыми являются только события хода; текст ответа приходит целиком |

## 7. Будущий функционал

Класс запроса `reminder` и структура запроса на напоминание `{due_at, text}`.
