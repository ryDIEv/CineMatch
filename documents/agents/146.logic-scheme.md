## 1. Порядок шагов

| № | Шаг | Что проверяется | Результат |
|---|---|---|---|
| 1 | Приём сообщения | текст не пуст, ≤ 1000 символов | иначе `INVALID_INPUT` / `INPUT_TOO_LONG` |
| 2 | Загрузка пользователя и сессии | согласие, город, этап, срок сессии | этап и `SessionState` (восстановление — [120 §3](120.data-model.md#3-сессия-и-восстановление)) |
| 3 | `/start` | точное совпадение | приветствие этапа, выход без модели |
| 4 | Инварианты этапа | `consent`, `onboarding`, `confirm_delete` | действие этапа или переход к диалогу |
| 5 | Классификатор | промпт по этапу | класс запроса |
| 6 | Ветвление | `cinema` / `delete_data` / `off_topic` / `unsafe` | вызов агента или отказ без модели |
| 7 | Агент | цикл вызовов модели и инструментов | `AgentOutput` |
| 8 | Проверка ответа | схема, фильмы из поиска, длины, число фильмов | подборка или повтор/ошибка |
| 9 | Сборка ответа | склейка карточек, трасса, этап | `AgentResponse` |
| 10 | Сохранение | сессия, история, события | журнал |

## 2. Псевдокод

```python
def handle_user_turn(user_id, message, movie_id=None, on_progress=None):
    progress = on_progress or (lambda step, text: None)

    if not message.strip():
        return error("INVALID_INPUT")
    if len(message) > 1000:
        return error("INPUT_TOO_LONG")

    user = get_user(user_id)
    session = load_or_restore_session(user)      # 120 §3
    progress("classify", "Определяю, что вы написали…")

    if message == "/start":
        return start_response(user, session)      # §3 этого документа

    if session.stage == "consent":
        cls = classify(message, stage="consent")  # yes / no
        if cls == "yes":
            return set_consent(user_id, True)
        return consent_response(again=True)

    if session.stage == "onboarding":
        return onboarding_turn(user, session, message)

    if session.stage == "confirm_delete":
        cls = classify(message, stage="confirm_delete")
        return delete_turn(user_id, session, confirmed=(cls == "yes"))

    # stage == "dialog"
    cls = classify(message, stage="dialog")       # cinema / delete_data / off_topic / unsafe
    if cls == "delete_data":
        session.stage = "confirm_delete"
        save(session)
        return confirmation("Удалить оценки, историю и настройки? …")
    if cls in ("off_topic", "unsafe"):
        log("OffTopicRejected", cls=cls)
        return message_response(OFF_TOPIC_TEXT)

    output, trace = run_agent(user, session, message, movie_id, progress)
    movies = validate(output, trace)              # 120 §5
    session = update_session(session, output, movies)
    save(session)
    return AgentResponse(type=type_of(output), text=output.text,
                         movies=movies, trace=trace, stage=session.stage)
```

## 3. Служебное сообщение `/start`

1. API-слой отправляет `/start` при открытии страницы после `GET /api/v1/session`.
2. Оркестратор обрабатывает его до классификатора, до загрузки промптов агента и до вызова модели.
3. В `messages` и `shown_ids` сообщение не попадает; трасса пуста.
4. Ответ зависит от этапа:

| Этап | `type` | Содержание ответа |
|---|---|---|
| `consent` | `consent` | правила хранения данных и две кнопки: «Принимаю» / «Не сейчас» |
| `onboarding` | `question` | приветствие и просьба назвать город |
| `dialog` | `message` | приветствие; если есть неоценённый выбор — `feedback_question` с вопросом об оценке |
| `confirm_delete` | `confirmation` | напоминание о подтверждении удаления |

5. Других служебных команд нет. Сообщение, начинающееся с `/`, кроме точного `/start`, идёт обычным путём и, как правило, классифицируется как `off_topic`.

## 4. Согласие

```python
def set_consent(user_id, accepted):
    if accepted:
        save_consent(user_id, source="web")
        session.stage = "onboarding"
        save(session)
        return question(CITY_PROMPT)
    return consent_response(again=True)   # ничего не сохраняется
```

Вызовы: `POST /api/v1/consent {"accepted": true}` из интерфейса и текст на этапе `consent` (классификатор `confirm_delete.md`). Модель к согласию не допускается.

## 5. Этап `onboarding`: город

1. `resolve_city(name)` возвращает до 5 вариантов.
2. Один вариант — оркестратор сохраняет его через `save_user_settings` и переводит этап в `dialog`, ответ — приветствие и первый вопрос агента.
3. Несколько вариантов — ответ `question` со списком «название, регион, страна» и просьбой уточнить; выбор сохраняется при следующем сообщении.
4. Ноль вариантов — `AgentResponse(type="error", error_code="CITY_NOT_FOUND")` с текстом из [contracts §6](../overall/contracts.md#6-ошибки). Этап не меняется.
5. Модель на этом этапе не вызывается.

## 6. Этап `dialog`: агент

1. Перед вызовом агента оркестратор подставляет `user_id`, `exclude_ids` из `last_shown_ids`, город, погоду (если есть), последние оценки и профиль.
2. Агент работает циклом: вызов модели → вызов инструмента → результат → снова модель. Не больше 8 вызовов модели за ход.
3. Перед каждым вызовом инструмента — `progress("tool", <фраза>)` из [110 §4](110.ui-ux.md#4-фразы-хода-работы).
4. Ответ модели — `AgentOutput` по схеме. Пустой или невалидный — один повтор с `retry_invalid_output.md`.
5. Проверка ответа и сборка `AgentResponse` — [120 §5](120.data-model.md#5-проверка-ответа).
6. После ответа — `progress("check", "Проверяю подборку…")`.

## 7. Этап `confirm_delete`

| Ответ | Действие | Ответ пользователю |
|---|---|---|
| `yes` | `delete_user_data(user_id)`, очистка сессии | «Готово, данные удалены.» |
| `no` | этап → `dialog`, ничего не удаляется | короткое подтверждение, диалог продолжается |
| невалидно дважды | этап → `dialog`, данные сохраняются | отказ разобрать ответ, подтверждение отменено |

## 8. События хода работы

| Момент | `step` | Пример `text` |
|---|---|---|
| сразу при приёме сообщения | `classify` | «Определяю, что вы написали…» |
| перед вызовом инструмента | `tool` | «Смотрю ваши оценки…», «Ищу фильмы…» |
| после ответа модели | `check` | «Проверяю подборку…» |

События формирует только оркестратор; API-слой перекладывает их в SSE ([ui/130](../ui/130.api-contracts.md)). Ошибка обработчика записывается в журнал и не прерывает ход.

## 9. Лимиты и тайм-ауты

| Что | Значение | Поведение при превышении |
|---|---|---|
| Входное сообщение | 1000 символов | `INPUT_TOO_LONG` |
| Вызовов модели на сообщение | 8 | `LIMIT_EXCEEDED` |
| Запрос к RouterAI | `LLM_TIMEOUT_S` = 20 с | один повтор, затем `LLM_UNAVAILABLE` |
| Ход оркестратора | `TURN_TIMEOUT_S` = 45 с | `LIMIT_EXCEEDED` |
| Ожидание в API-слое | `AGENT_TIMEOUT_S` = 60 с | `AGENT_TIMEOUT` |

Значения и условие `LLM_TIMEOUT_S < TURN_TIMEOUT_S < AGENT_TIMEOUT_S` — [overall/config.md §2](../overall/config.md#2-тайм-ауты-и-целевые-значения).

## 10. Журнал

На каждый ход пишутся: `event=turn`, `user_id`, `stage`, `class`, `tool_calls`, `model_calls`, `duration_ms`, `tokens_in`, `tokens_out`, `result` (тип ответа или код ошибки). Отдельные события — [135](135.event-catalog.md), схемы — [140](140.event-schema.md). Текст сообщения пользователя и системный промпт в журнал не попадают.

## 11. Будущий функционал

Асинхронная ветка для напоминаний: агент-планировщик создаёт запись, доставку выполняет бот.
